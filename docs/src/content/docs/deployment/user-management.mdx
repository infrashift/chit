title: User Management
description: Creating and managing user identities and authorization for Chit.
---

Chit uses Ory Kratos for people's identities and Ory Hydra for machine
actors (agents and bots). Access to teams and channels is decided by Chit
itself from its PostgreSQL membership tables; Ory Keto authorizes slash
commands. This guide covers how to create users, manage sessions, and how
authorization works.

## How user provisioning works

Chit does not require you to create users in two places. The flow is:

1. **Create a Kratos identity** — this is the source of truth for authentication
2. **User logs in** — Oathkeeper validates the session and forwards `X-User-Id`
3. **Chit auto-provisions** — on first authenticated request, Chit fetches the
   identity from the Kratos Admin API and creates a local user record with the
   identity's traits (username, email, display name)

You only need to create the Kratos identity. Chit handles the rest.

Machine actors are different: they have no Kratos identity and are never
created on first use. Declare them in `CHIT_MACHINE_ACTORS` and chitd creates
or updates them at every boot; see
[Machine actors](/chit/reference/configuration/#machine-actors) and
[Headless Claude Code](/chit/deployment/headless-claude/).

`POST /api/v1/users` creates a user record directly. It is restricted to
`system_admin`, and is meant for cases neither path covers, such as
addressing a person who has never signed in.

## Prerequisites

| Dependency | Purpose |
|---|---|
| Kratos Admin API access (port 4434) | Create and manage identities |
| `curl` and `jq` | Command-line examples below |

## Creating users

### Via the Kratos Admin API

Create an identity with a password credential:

```bash
curl -s -X POST http://localhost:4434/admin/identities \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_id": "default",
    "traits": {
      "email": "newuser@example.com",
      "username": "newuser",
      "display_name": "New User"
    },
    "credentials": {
      "password": {
        "config": {
          "password": "SecurePassword123!"
        }
      }
    },
    "state": "active"
  }' | jq .
```

The response includes the generated identity ID:

```json
{
  "id": "generated-uuid-here",
  "traits": {
    "email": "newuser@example.com",
    "username": "newuser",
    "display_name": "New User"
  },
  "state": "active"
}
```

Save the `id` value — this is the Kratos identity ID that Chit uses as the
user's `X-User-Id`.

### With a specific identity ID

To assign a known UUID (useful for scripting and test environments):

```bash
curl -s -X POST http://localhost:4434/admin/identities \
  -H 'Content-Type: application/json' \
  -d '{
    "id": "aaaaaaaa-bbbb-4ccc-dddd-eeeeeeeeeeee",
    "schema_id": "default",
    "traits": {
      "email": "scripted@example.com",
      "username": "scripted",
      "display_name": "Scripted User"
    },
    "credentials": {
      "password": {
        "config": {
          "password": "SecurePassword123!"
        }
      }
    },
    "state": "active"
  }' | jq .
```

### Using the seed script (UAT only)

For the UAT environment, a seed script creates all 5 test users at once:

```bash
make uat-seed-kratos
```

This creates Kratos identities with known UUIDs matching the pre-seeded Chit
database users. The UAT seeder (built from `scripts/seed-uat/main.go`) also
creates a `chit-agent` user with `actor_type=agent`, added to the UAT team
and channel — set `CHIT_MCP_AGENT_KRATOS_ID` to its Kratos ID to run the MCP server
against UAT. See [Manual Acceptance Testing](/chit/getting-started/manual-acceptance-testing/)
for details.

## Identity schema

Chit's Kratos identity schema requires three traits:

| Trait | Type | Constraints | Purpose |
|---|---|---|---|
| `email` | string (email) | Required, used as login identifier | Authentication credential |
| `username` | string | 2–64 chars, `^[a-z0-9][a-z0-9._-]{0,62}[a-z0-9]$` | Display in UI, @mentions |
| `display_name` | string | 1–100 chars | Shown in message headers |

The schema is defined in the `chit-kratos-config` ConfigMap in
`deploy/chit.kube.yml`.

## Managing users

### List all identities

```bash
curl -s http://localhost:4434/admin/identities | jq '.[].traits'
```

### Get a specific identity

```bash
curl -s http://localhost:4434/admin/identities/IDENTITY_ID | jq .
```

### Update identity traits

```bash
curl -s -X PUT http://localhost:4434/admin/identities/IDENTITY_ID \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_id": "default",
    "traits": {
      "email": "updated@example.com",
      "username": "updateduser",
      "display_name": "Updated Name"
    },
    "state": "active"
  }' | jq .
```

:::caution
Updating traits in Kratos does **not** update the Chit local user record,
which is only populated during auto-provisioning (first login). A user changes
their own Chit username and display name with `PUT /api/v1/users/me`:

```bash
curl -s -X PUT -H "X-Session-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"username": "newname", "display_name": "New Name"}' \
  http://localhost:4455/api/v1/users/me | jq .
```

Either field may be omitted. The username is lowercased and must match the
schema pattern above; a username already taken answers 409. Email and roles
cannot be changed through the API.
:::

### Delete an identity

```bash
curl -s -X DELETE http://localhost:4434/admin/identities/IDENTITY_ID
```

This stops the person from logging in. Their Chit user record and messages
remain.

### Reset a user's password

```bash
curl -s -X PUT http://localhost:4434/admin/identities/IDENTITY_ID \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_id": "default",
    "traits": {
      "email": "user@example.com",
      "username": "username",
      "display_name": "Display Name"
    },
    "credentials": {
      "password": {
        "config": {
          "password": "NewPassword123!"
        }
      }
    },
    "state": "active"
  }' | jq .
```

## Sessions

### How sessions work

1. User submits credentials to Kratos login flow
2. Kratos returns a **session token**
3. Client sends `X-Session-Token` header on every request to Oathkeeper
4. Oathkeeper validates the session with Kratos (`/sessions/whoami`)
5. On success, Oathkeeper sets `X-User-Id` header and forwards to Chit

chit-tui (in this monorepo under `clients/chit-tui`) stores the session
token at `~/.config/chit-tui/session.json` and reuses it on subsequent
launches.

### Invalidate a user's sessions

To force a user to re-authenticate, delete their active sessions:

```bash
curl -s -X DELETE \
  http://localhost:4434/admin/identities/IDENTITY_ID/sessions
```

### Check an active session

```bash
curl -s -H "X-Session-Token: SESSION_TOKEN" \
  http://localhost:4433/sessions/whoami | jq .
```

## Authorization

Team and channel access is decided by chitd from the `team_members` and
`channel_members` tables in PostgreSQL. The rules:

- **Teams.** Anyone may create a team and becomes its `team_admin`. Renaming
  or deleting a team requires `team_admin` or `system_admin`; deleting it
  deletes its channels. Invite-only teams are visible only to their members
  and to system admins, and `GET /api/v1/teams` lists open teams plus the
  caller's own. Only members (and system admins) may list a team's members.
  Adding a member requires being a member; removing anyone but yourself
  requires `system_admin`. A user removed from a team is removed from all of
  that team's channels.
- **Channels.** `POST /api/v1/channels` creates open (`O`) or private (`P`)
  channels only, needs a `team_id`, and requires the creator to be on that
  team. A new open channel includes everyone on the team at that moment;
people who join the team later join its open channels themselves. Anyone on
  the team may see an open channel and add members to it; private channels
  only by their members. A user added to an open or private channel must be on
  its team. Removing anyone but yourself requires `system_admin`; deleting a
  channel requires being its creator or `system_admin`.
- **Direct and group channels** are created with `/channels/direct` and
  `/channels/group`, must include the caller, and have fixed membership: no
  one can be added later.
- **Reading.** Posts, members and the details of private, direct and group
  channels are readable by channel members only.
- **Slash commands** require channel membership and a Keto `execute` grant
  (below).

### Keto namespaces

| Namespace | Object | Relation | Subject | Meaning |
|---|---|---|---|---|
| `chit/command` | `Command:{id}` | `execute` | `Actor:{id}` | User can execute the command |
| `chit/channel` | Channel ID | `member` | User ID | Mirror of channel membership |

Keto is authoritative only for slash commands. chitd mirrors channel
membership into `chit/channel` on a best-effort basis: a failed write does not
fail the request and is not retried, and members added when a channel is
created are written in the background, after the response. chitd never reads that namespace, so the tuples are useful
for inspection but **writing or deleting them does not grant or revoke
access**. Use the channel member endpoints for that.

### Inspecting the channel mirror

**Check whether Keto has a user as a channel member:**

```bash
curl -s -X POST http://localhost:4466/relation-tuples/check \
  -H 'Content-Type: application/json' \
  -d '{
    "namespace": "chit/channel",
    "object": "CHANNEL_ID",
    "relation": "member",
    "subject_id": "USER_ID"
  }' | jq .
```

Response: `{"allowed": true}` or `{"allowed": false}`

**List all members Keto has for a channel:**

```bash
curl -s "http://localhost:4466/relation-tuples?namespace=chit/channel&object=CHANNEL_ID" \
  | jq '.relation_tuples[].subject_id'
```

## System admin role

Alice (`alice@example.com`) is assigned the `system_admin` role in the Chit
database during UAT seeding. Other users are assigned `system_user`. A system
admin can create users (`POST /api/v1/users`), rename or delete any team,
see invite-only teams, remove other members from teams and channels, and
delete any channel.

Roles are stored in the Chit database (`users.roles`, space-separated), not
in Kratos or Keto. No API endpoint changes them: grant `system_admin` to a
person by updating that column, and to a machine actor through its `roles`
in `CHIT_MACHINE_ACTORS`.

## End-to-end example

Create a new user and verify they can log in and access channels:

```bash
# 1. Create the Kratos identity
IDENTITY=$(curl -s -X POST http://localhost:4434/admin/identities \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_id": "default",
    "traits": {
      "email": "frank@example.com",
      "username": "frank",
      "display_name": "Frank Foster"
    },
    "credentials": {
      "password": {
        "config": {
          "password": "Password1!"
        }
      }
    },
    "state": "active"
  }')
echo "$IDENTITY" | jq .id

# 2. Log in through Oathkeeper to get a session token
FLOW=$(curl -s http://localhost:4455/kratos/self-service/login/api | jq -r .id)
TOKEN=$(curl -s -X POST \
  -H 'Content-Type: application/json' \
  -d '{"method":"password","identifier":"frank@example.com","password":"Password1!"}' \
  "http://localhost:4455/kratos/self-service/login?flow=$FLOW" \
  | jq -r .session_token)
echo "Session token: $TOKEN"

# 3. Make an authenticated request — Chit auto-provisions the user
curl -s -H "X-Session-Token: $TOKEN" \
  http://localhost:4455/api/v1/users/me | jq .

# 4. List visible teams (open teams plus the user's own)
curl -s -H "X-Session-Token: $TOKEN" \
  http://localhost:4455/api/v1/teams | jq .
```

After step 3, the user exists in Chit's database. A member of a team can then
add them to it (`POST /api/v1/teams/{id}/members`), after which they can see
and join that team's open channels.
