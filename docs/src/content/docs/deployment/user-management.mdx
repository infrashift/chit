title: User Management
description: Creating and managing user identities and authorization for Chit.
---

Chit uses Ory Kratos for people's identities and Ory Hydra for machine
actors (agents and bots). Chit itself decides access to teams and channels
from its PostgreSQL membership tables. Ory Keto authorizes slash
commands. This guide covers how to create users, manage sessions, and how
authorization works.

## How user provisioning works

Chit does not require you to create users in two places. The flow is:

1. **Create a Kratos identity** — this is the source of truth for authentication
2. **User logs in** — Oathkeeper validates the session and forwards `X-User-Id`
3. **Chit auto-provisions** — on the first authenticated request, Chit fetches
   the identity from the Kratos Admin API. Then it creates a local user record
   with the identity's traits (username, email, display name)

You only need to create the Kratos identity. Chit handles the rest.

Machine actors are different: they have no Kratos identity and are never
created on first use. Declare them in `CHIT_MACHINE_ACTORS` and chitd creates
or updates them at every boot; see
[Machine actors](/chit/reference/configuration/#machine-actors) and
[Headless Claude Code](/chit/deployment/headless-claude/).

`POST /api/v1/users` creates a user record directly. Only `system_admin` can
use it. It is for cases that neither path covers, for example to address a
person who has never signed in.

## Prerequisites

| Dependency | Purpose |
|---|---|
| Kratos Admin API access (port 4434) | Create and manage identities |

## Creating users

### Via the Kratos Admin API

Create an identity with a password credential:

```bash
curl -s -X POST http://localhost:4434/admin/identities \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_id": "default",
    "traits": {
      "email": "newuser@example.com",
      "username": "newuser",
      "display_name": "New User"
    },
    "credentials": {
      "password": {
        "config": {
          "password": "SecurePassword123!"
        }
      }
    },
    "state": "active"
  }' | jq .
```

The response includes the generated identity ID:

```json
{
  "id": "generated-uuid-here",
  "traits": {
    "email": "newuser@example.com",
    "username": "newuser",
    "display_name": "New User"
  },
  "state": "active"
}
```

Save the `id` value — this is the Kratos identity ID that Chit uses as the
user's `X-User-Id`.

### With a specific identity ID

To assign a known UUID (useful for scripts and test environments):

```bash
curl -s -X POST http://localhost:4434/admin/identities \
  -H 'Content-Type: application/json' \
  -d '{
    "id": "aaaaaaaa-bbbb-4ccc-dddd-eeeeeeeeeeee",
    "schema_id": "default",
    "traits": {
      "email": "scripted@example.com",
      "username": "scripted",
      "display_name": "Scripted User"
    },
    "credentials": {
      "password": {
        "config": {
          "password": "SecurePassword123!"
        }
      }
    },
    "state": "active"
  }' | jq .
```

### Using the seed script (UAT only)

For the UAT environment, a seed script creates all 5 test users at once:

```bash
make uat-seed-kratos
```

This creates Kratos identities with known UUIDs. The UUIDs are the same as
those of the pre-seeded Chit database users. The UAT seeder (built from
`scripts/seed-uat/main.go`) also creates a `chit-agent` user with
`actor_type=agent` and adds it to the UAT team and channel. To run the MCP server
against UAT, set `CHIT_MCP_AGENT_KRATOS_ID` to its Kratos ID. See [Manual Acceptance Testing](/chit/getting-started/manual-acceptance-testing/)
for details.

## Identity schema

Chit's Kratos identity schema requires three traits:

| Trait | Type | Constraints | Purpose |
|---|---|---|---|
| `email` | string (email) | Required, used as login identifier | Authentication credential |
| `username` | string | 2–64 chars, `^[a-z0-9][a-z0-9._-]{0,62}[a-z0-9]$` | Display in UI, @mentions |
| `display_name` | string | 1–100 chars | Shown in message headers |

The `chit-kratos-config` ConfigMap in `deploy/chit.kube.yml` defines the
schema.

## Managing users

### List all identities

```bash
curl -s http://localhost:4434/admin/identities | jq '.[].traits'
```

### Get a specific identity

```bash
curl -s http://localhost:4434/admin/identities/IDENTITY_ID | jq .
```

### Update identity traits

```bash
curl -s -X PUT http://localhost:4434/admin/identities/IDENTITY_ID \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_id": "default",
    "traits": {
      "email": "updated@example.com",
      "username": "updateduser",
      "display_name": "Updated Name"
    },
    "state": "active"
  }' | jq .
```

:::caution
A change to traits in Kratos does **not** update the Chit local user record.
Chit fills that record only at auto-provisioning (first login). A user changes
their own Chit username and display name with `PUT /api/v1/users/me`:

```bash
curl -s -X PUT -H "X-Session-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"username": "newname", "display_name": "New Name"}' \
  http://localhost:4455/api/v1/users/me | jq .
```

The user can leave out either field. Chit changes the username to lowercase,
and the username must match the schema pattern above. A username that another
user has answers 409. The API cannot change email or roles.
:::

### Delete an identity

```bash
curl -s -X DELETE http://localhost:4434/admin/identities/IDENTITY_ID
```

This stops the person from logging in. Their Chit user record and messages
remain.

### Reset a user's password

```bash
curl -s -X PUT http://localhost:4434/admin/identities/IDENTITY_ID \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_id": "default",
    "traits": {
      "email": "user@example.com",
      "username": "username",
      "display_name": "Display Name"
    },
    "credentials": {
      "password": {
        "config": {
          "password": "NewPassword123!"
        }
      }
    },
    "state": "active"
  }' | jq .
```

## Sessions

### How sessions work

1. User submits credentials to Kratos login flow
2. Kratos returns a **session token**
3. Client sends `X-Session-Token` header on every request to Oathkeeper
4. Oathkeeper validates the session with Kratos (`/sessions/whoami`)
5. On success, Oathkeeper sets `X-User-Id` header and forwards to Chit

chit-tui (in this monorepo under `clients/chit-tui`) stores the session
token at `~/.config/chit/session.json` and reuses it on subsequent
launches.

### Invalidate a user's sessions

To force a user to re-authenticate, delete their active sessions:

```bash
curl -s -X DELETE \
  http://localhost:4434/admin/identities/IDENTITY_ID/sessions
```

### Check an active session

```bash
curl -s -H "X-Session-Token: SESSION_TOKEN" \
  http://localhost:4433/sessions/whoami | jq .
```

## Authorization

chitd decides team and channel access from the `team_members` and
`channel_members` tables in PostgreSQL. The rules:

- **Teams.** Anyone may create a team and becomes its `team_admin`. To rename
  or delete a team, a user must have `team_admin` or `system_admin`. When a
  user deletes a team, chitd deletes its channels. Only their members and
  system admins can see invite-only teams. `GET /api/v1/teams` lists open teams
  plus the caller's own. Only members (and system admins) may list a team's
  members. Anyone may join an open team themselves. Only a member can add
  another user or join an invite-only team. To remove another user, a user
  must have `system_admin`. When chitd removes a user from a team, it also
  removes the user from all of that team's channels.
- **Channels.** `POST /api/v1/channels` creates open (`O`) or private (`P`)
  channels only. It needs a `team_id`, and the creator must be on that
  team. A new open channel includes everyone on the team at that moment.
  People who join the team later join its open channels themselves. Anyone on
  the team may see an open channel and add members to it. For a private
  channel, only its members can do this. A user added to an open or private
  channel must be on its team. To remove another user, a user must have
  `system_admin`. Only the creator or a `system_admin` can delete a channel.
- **Direct and group channels.** `/channels/direct` and `/channels/group`
  create them. They must include the caller, and their membership does not change:
  nobody can add a member later.
- **Read access.** Only channel members can read the posts, the members and
  the details of private, direct and group channels.
- **Slash commands** require channel membership and a Keto `execute` grant
  (below).

### Keto namespaces

| Namespace | Object | Relation | Subject | Meaning |
|---|---|---|---|---|
| `chit/command` | `Command:{id}` | `execute` | `Actor:{id}` | User can execute the command |
| `chit/channel` | Channel ID | `member` | User ID | Mirror of channel membership |

Keto is authoritative only for slash commands. chitd mirrors channel
membership into `chit/channel` on a best-effort basis. A failed write does not
fail the request, and chitd does not retry it. When a user creates a channel,
chitd writes the tuples of its first members in the background, after the
response. chitd never reads that namespace. The tuples help you to examine
membership, but **to write or delete them does not grant or revoke
access**. Use the channel member endpoints for that.

### Inspecting the channel mirror

**Check whether Keto has a user as a channel member:**

```bash
curl -s -X POST http://localhost:4466/relation-tuples/check \
  -H 'Content-Type: application/json' \
  -d '{
    "namespace": "chit/channel",
    "object": "CHANNEL_ID",
    "relation": "member",
    "subject_id": "USER_ID"
  }' | jq .
```

Response: `{"allowed": true}` or `{"allowed": false}`

**List all members Keto has for a channel:**

```bash
curl -s "http://localhost:4466/relation-tuples?namespace=chit/channel&object=CHANNEL_ID" \
  | jq '.relation_tuples[].subject_id'
```

## System admin role

The UAT seed data gives Alice (`alice@example.com`) the `system_admin` role
in the Chit database. Other users get `system_user`. A system admin can create
users (`POST /api/v1/users`) and rename or delete any team. A system admin can
also see invite-only teams, remove other members from teams and channels, and
delete any channel.

The Chit database stores roles (`users.roles`, space-separated), not
Kratos or Keto. No API endpoint changes them. To grant `system_admin` to a
person, update that column. To grant it to a machine actor, set its `roles`
in `CHIT_MACHINE_ACTORS`.

## End-to-end example

Create a new user and verify they can log in and access channels:

```bash
# 1. Create the Kratos identity
IDENTITY=$(curl -s -X POST http://localhost:4434/admin/identities \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_id": "default",
    "traits": {
      "email": "frank@example.com",
      "username": "frank",
      "display_name": "Frank Foster"
    },
    "credentials": {
      "password": {
        "config": {
          "password": "Password1!"
        }
      }
    },
    "state": "active"
  }')
echo "$IDENTITY" | jq .id

# 2. Log in through Oathkeeper to get a session token
FLOW=$(curl -s http://localhost:4455/kratos/self-service/login/api | jq -r .id)
TOKEN=$(curl -s -X POST \
  -H 'Content-Type: application/json' \
  -d '{"method":"password","identifier":"frank@example.com","password":"Password1!"}' \
  "http://localhost:4455/kratos/self-service/login?flow=$FLOW" \
  | jq -r .session_token)
echo "Session token: $TOKEN"

# 3. Make an authenticated request — Chit auto-provisions the user
curl -s -H "X-Session-Token: $TOKEN" \
  http://localhost:4455/api/v1/users/me | jq .

# 4. List visible teams (open teams plus the user's own)
curl -s -H "X-Session-Token: $TOKEN" \
  http://localhost:4455/api/v1/teams | jq .
```

After step 3, the user exists in Chit's database. They can join an open team
themselves (`POST /api/v1/teams/{id}/members` with their own `user_id`); a
member of an invite-only team must add them. On the team, they can see and
join its open channels.
