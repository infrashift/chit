description: Deploying the Chit stack with Podman Kube.

`deploy/chit.kube.yml` defines Chit's local stack, chitd included. A single
command starts it, with no Docker Compose. The manifest
defines two pods: `chit-db`, which runs PostgreSQL, and `chit-app`, which waits
for it, runs the migrations and starts everything else.

## Pod Contents

### `chit-db`

| Container | Image | Port(s) | Purpose |
|---|---|---|---|
| **postgres** | TSC `postgresql17:17.12-9410cd4` | 5432 | Primary data store; also holds the `kratos`, `keto` and `hydra` databases |

### `chit-app`

Init containers run in order before the services start:

| Init container | Image | Purpose |
|---|---|---|
| **wait-postgres** | TSC `postgresql17:17.12-9410cd4` | Waits until PostgreSQL accepts connections |
| **ensure-databases** | TSC `postgresql17:17.12-9410cd4` | Creates the `kratos`, `keto` and `hydra` databases if missing, on every start |
| **migrate-kratos** | TSC `kratos:v26.2.0` | Kratos schema migrations |
| **migrate-keto** | TSC `keto-cue:v0.0.0-20261114211924-809351b32b9c-6a44b89` | keto-cue schema migrations |
| **migrate-hydra** | TSC `hydra:v26.2.0` | Hydra schema migrations |
| **migrate-chit** | `migrate/migrate:v4.15.0` | Chit schema migrations from `migrations/` (mounted from the checkout) |

Then the services:

| Container | Image | Port(s) | Purpose |
|---|---|---|---|
| **kratos** | TSC `kratos:v26.2.0` | 4433, 4434 | Identity management (people) |
| **keto** | TSC `keto-cue:v0.0.0-20261114211924-809351b32b9c-6a44b89` | 4466, 4467 | Slash-command authorization (keto-cue, CUE schema) |
| **hydra** | TSC `hydra:v26.2.0` | 4444, 4445 | OAuth2 tokens for machine actors (`--dev`: plain HTTP) |
| **oathkeeper** | TSC `oathkeeper:v26.2.0` | 4455, 4456 | Authentication proxy |
| **zincsearch** | `zinclabs/zincsearch:0.4.10` | 4080 | Full-text search index |
| **seaweedfs** | TSC `seaweedfs:4.51-382cdac` | 8333 (S3), 9333, 8380, 8888; gRPC 19333, 18380, 18888, 18334; all on 127.0.0.1 | Attachment store: one `weed server` with master, volume server, filer and S3 gateway. The gateway accepts only the identity in `chit-seaweedfs-config`. chitd creates the `chit-files` bucket. |
| **memberhook-stub** | `golang:1.26-alpine` (the builder image of `deploy/Containerfile`) | 4490 on 127.0.0.1 | A stub of HALO's membership hook for the stack e2e, `go run` from `tests/e2e/hookstub` in the checkout. It registers chitd's Hydra client `chit-e2e-memberhook` and allows every member until the e2e names one to refuse. Test only. |
| **chitd** | `localhost/chit:latest` | 8065 | The Chit server |

The manifest gives the chitd container these settings:

- the database URL;
- the Kratos and Keto URLs;
- the ZincSearch URL and credentials;
- the SeaweedFS endpoint and its dev S3 key (`CHIT_S3_*`);
- the e2e machine actors;
- the membership hook (`CHIT_MEMBERSHIP_HOOK_*`, which points at
  `memberhook-stub`).

All other settings take the defaults of chitd. To set more (for example
`CHIT_MACHINE_ACTORS` or `CHIT_TRUSTED_PROXY_SECRET`), add it to the `env` of
the `chitd` container and run `make kube-restart`. Alternatively, run chitd
locally with `.env` (see [Startup Order](#startup-order)).

Podman names each container `<pod>-<container>`, e.g. `chit-app-chitd`.

The manifest pins every image by digest. "TSC" is
`ghcr.io/infrashift/trusted-service-containers`; SeaweedFS is its
`trusted/seaweedfs`, built from source on UBI9 Micro. PostgreSQL is its
`trusted/postgresql17`: the signed PGDG RPMs, contrib included, on UBI9
Minimal. It runs as UID 26 with primary group 0, and refuses to run as root.
It keeps the `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` contract of
the Docker images. ZincSearch,
`migrate/migrate` and the Go builder image are not in TSC and come from
their upstream registries.
TSC builds keto-cue from source (commit `809351b3`) on trusted UBI9 Micro,
the same way it builds the Ory images.

## Persistent Volumes

| PVC | Mount | Purpose |
|---|---|---|
| `chit-pgdata` | `/var/lib/pgsql/data` | PostgreSQL data; the cluster is in `userdata/` (`PGDATA=/var/lib/pgsql/data/userdata`), owned by UID 26 |
| `chit-zincdata` | `/data` | ZincSearch index data |
| `chit-seaweeddata` | `/data` | SeaweedFS volumes and filer metadata (attachments) |

### Upgrading from the DHI PostgreSQL image

Before the switch to `trusted/postgresql17`, `chit-pgdata` held a cluster of
the DHI `postgres:17-debian` mirror. UID 70 owns this cluster. It is at
`/var/lib/postgresql/17/data`, and its `LC_COLLATE` is the glibc
`en_US.UTF-8` locale. The new
image cannot start on that volume, and it has no `en_US.UTF-8` locale, so move
the data with a dump and a restore:

```bash
# 1. With the old checkout and the old stack still running:
podman exec chit-db-postgres pg_dumpall -U chit > chit-pgdumpall.sql
tail -n 3 chit-pgdumpall.sql   # must end with "PostgreSQL database cluster dump complete"

# 2. Stop the stack and delete only the PostgreSQL volume. make kube-clean
#    would also delete the search index and the attachments.
make kube-down
podman volume rm chit-pgdata

# 3. Pull the new checkout, then restore into a fresh chit-pgdata.
#    PG_IMAGE is the image the Makefile and the manifests pin.
PG_IMAGE=ghcr.io/infrashift/trusted-service-containers/trusted/postgresql17:17.12-9410cd4@sha256:6375c284b5aaa6d83096d74ae6b1b7a3340bcd81739e4309465b18a3e781d6e3
podman run -d --name chit-pg-restore -v chit-pgdata:/var/lib/pgsql/data \
  -e POSTGRES_USER=chit -e POSTGRES_PASSWORD=chit -e POSTGRES_DB=chit "$PG_IMAGE"
until podman exec chit-pg-restore pg_isready -U chit -d chit; do sleep 1; done
for db in kratos keto hydra; do podman exec chit-pg-restore createdb -U chit "$db"; done
podman exec -i chit-pg-restore psql -U chit -d postgres -q < chit-pgdumpall.sql
podman stop chit-pg-restore && podman rm chit-pg-restore

# 4. Start the stack on the restored volume.
make kube-up
```

The restore prints `ERROR: role "chit" already exists` and one
`ERROR: invalid LC_COLLATE locale name: "en_US.UTF-8"` for each database. Both
are normal: the role and the databases already exist, and the rest of the
dump goes into them. Examine any other error before you serve traffic.
The restored databases sort text with the builtin `C.UTF-8` locale, and
PostgreSQL builds every index again with it.

If the volume has no data to keep, you must still create it again. Run
`make kube-clean` (or `make uat-clean` for the UAT stack) one time. The next
`make kube-up` (or `make uat-up`) initialises an empty volume.

## Networking

The pods run with `--network host`, so all containers share the host network
namespace. Each service is reachable at `localhost` on its configured port,
and Oathkeeper forwards `/api/v1/**` to whatever listens on `localhost:8065`.

## Containerfile

`make kube-build` builds the server image from `deploy/Containerfile`:

```bash
make kube-build
```

The Containerfile uses a multi-stage build. A `golang:1.26-alpine` builder
stage compiles `chitd` and `chit-reconcile`. Then a `ubi9-minimal` runtime
image runs as a non-root `chit` user. It carries the CUE definitions at
`/etc/chit/auth` (`CHIT_COMMANDS_CUE_DIR`) and starts `chitd`.

## Test Containerfile

A separate Containerfile at `Containerfiles/Containerfile.test` builds a UBI9
image with the full Go toolchain to run unit tests. The unit tests use
in-memory fakes. They need no PostgreSQL or Ory services.

```bash
make test-container
```

The image compile-gates at build time (`go build ./...`), then streams test
output at run time. You can override the default `CMD` to run specific tests:

```bash
podman run --rm chit-test:latest go test -run TestSpecific ./internal/model/...
```

## Startup Order

1. `make kube-up` builds the image and starts both pods. The init containers
   create the databases and run the Kratos, Keto, Hydra and Chit migrations.
   Then the services, chitd included, start.
2. Check chitd: `curl http://localhost:8065/api/v1/system/ping`.

To work on chitd itself, stop the pod's copy so `:8065` is free. Then run the
local build in its place:

```bash
podman stop chit-app-chitd
cp .env.example .env
make run
```

`podman start chit-app-chitd` brings the containerized one back. If you later
add new migration files, apply them to the pod with
`make kube-migrate`. The pod does not need a restart.
