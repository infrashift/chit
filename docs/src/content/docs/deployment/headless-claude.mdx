---
title: Headless Claude Code
description: Drive headless Claude Code sessions from Chit channels with the chit-claude bridge.
---

The `chit-claude` bridge turns Chit into an asynchronous, markdown-native
front-end for [Claude Code](https://code.claude.com/docs). Name the agent in a
configured channel. The bridge then runs `claude -p` headlessly in a work
directory that the operator selects. Claude's response comes back to the thread
as the agent user, with a token/cost footer. A reply in the thread resumes the
same Claude session, with its full context. So a task can continue for hours or
days with no terminal open anywhere.

## How it works

```
you (any Chit client)
   │  post "@claude-architect plan the migration of service X"
   ▼
chitd ──WebSocket (posted event)──▶ chit-claude bridge
                                        │ claude -p --output-format json
                                        │   --strict-mcp-config --setting-sources project
                                        │   (adds --resume <session_id> on thread replies)
                                        │ stdin: "[@you] @claude-architect plan the…"
                                        ▼
                                    claude CLI ──▶ Anthropic (subscription OAuth)
                                        │ result JSON: text + session_id + usage
                                        ▼
chitd ◀──REST POST /posts (threaded reply + footer + session prop)──┘
```

- **Thread = session.** A root post starts a new Claude session. The bridge
  stores the returned `session_id` in the agent reply's `props`
  (`claude_session_id`), so state lives in the conversation itself and
  survives bridge restarts. Replies in the thread run
  `claude -p --resume <session_id>`.
- **The prompt goes in on stdin, tagged with its author.** Claude reads
  `[@alice] …`, so it can tell the people in a thread apart. The bridge adds
  nothing else to a turn; see [token cost](#token-cost).
- **One run at a time per thread, a few at a time overall.** Messages that
  arrive while Claude works wait in a queue, in order. If two processes
  resumed the same session at once, they could interleave its transcript.
  `CHIT_CLAUDE_MAX_CONCURRENT_RUNS` (default 2) caps runs across threads.
- **Runs stay apart from the host's Claude Code setup.** Every run passes
  `--strict-mcp-config`, so no MCP server loads unless
  `CHIT_CLAUDE_MCP_CONFIG` names it. Every run also passes
  `--setting-sources project`, so the host user's own settings (and the
  permissions, hooks and plugins they enable) stay out. The bridge posts the `--output-format json` result
  itself. To let Claude read Chit or post mid-run updates, give it
  `chit-mcp` through `CHIT_CLAUDE_MCP_CONFIG`.
- **Failures are visible.** A failed or timed-out run posts an error reply to
  the thread. It does not stay silent. It shows the CLI's own message (or the
  first line of stderr); the full stderr goes to the bridge's log.

:::caution[How to resume a session]
`claude -p --session-id <id>` does **not** resume a session on later runs.
That flag assigns an ID to a *new* session. To resume, run
`claude -p --resume <session_id>` with the `session_id` from the
previous run's JSON output. The bridge does this for you. This note is here
because most hand-rolled scripts get it wrong.
:::

## Setup

### 1. Give the agent an OAuth2 client

Agents authenticate to Chit with an Ory Hydra access token from the
`client_credentials` grant. The agent presents the token to Oathkeeper.
Oathkeeper introspects it and enforces the token's audience and scope. Only then
does it forward the request to chitd, with the token's `client_id` in
`X-Client-Id`.

Create the client in Hydra (the `make kube-up` stack runs it, admin API on
`:4445`):

```bash
HYDRA_ADMIN=http://localhost:4445

# Hydra generates the client_id and secret. Note both — the secret is
# shown once.
curl -sS -X POST "$HYDRA_ADMIN/admin/clients" \
  -H 'Content-Type: application/json' -d '{
    "client_name":                "claude-architect",
    "grant_types":                ["client_credentials"],
    "token_endpoint_auth_method": "client_secret_post",
    "scope":                      "chit:read chit:write",
    "audience":                   ["chit"]
  }'
```

Either `client_secret_post` or `client_secret_basic` works — Hydra enforces
whichever the client registered and rejects the other with `invalid_client`,
so the bridge auto-detects rather than pinning one.

**Scopes.** `chit:read` covers every `GET` (the WebSocket upgrade too).
`chit:write` covers `POST`/`PUT`/`DELETE`. The bridge needs both: it listens
over the WebSocket and posts replies. Chit's search and batch-tag endpoints
only read, but they are `POST`s. So they also need `chit:write`. A strictly
read-only token can list and fetch but cannot search.

**Audience.** The `chit` audience keeps apart the applications that share the
gateway. Oathkeeper's rules reject a token minted for another audience, even
when it is a valid Hydra token.

### 2. Declare the agent user

A machine actor has no Kratos identity and no email. chitd never creates its
user on first use. chitd answers 401 to a token for a client that it does not
know.
Declare the agent in chitd's environment with `CHIT_MACHINE_ACTORS`, a JSON
array with one entry per client:

```bash
CHIT_MACHINE_ACTORS='[
  {"client_id": "<client_id from step 1>", "username": "claude-architect",
   "display_name": "Claude Architect", "actor_type": "agent"}
]'
```

Each entry must have `actor_type`, and it must be `agent` for a bridge persona
(`bot` is the other accepted value). `roles` is optional, space-separated, and
defaults to `system_user`; `system_admin` is a real grant, so leave it out
unless the agent needs it. See the
[configuration reference](/chit/reference/configuration/#machine-actors) for
every field.

chitd reconciles the list at every boot, before it accepts requests. It
creates each actor that does not exist yet. It updates `username`,
`display_name`, `roles` and `actor_type` to agree with the declaration. So an
edit takes effect on the next restart. If you remove an entry, chitd does not
delete the user. An invalid entry stops chitd at startup.

In the `make kube-up` stack, chitd's environment is the `chitd` container in
`deploy/chit.kube.yml`. Add `CHIT_MACHINE_ACTORS` to its `env` and run
`make kube-restart`. As an alternative, run chitd yourself with `make run`, and
set the variable in `.env`.

:::caution[The binding is the identity]
For the `client_credentials` grant, Hydra sets the token's `sub` to the
generated `client_id`. Hydra does **not** expose client metadata when it
introspects a token. So Chit resolves the client against
`users.oauth_client_id`, which is the declaration's `client_id`. Chit rejects a
client with no binding at once. Chit provisions an unknown Kratos ID into a
new user, but it never does this for a client.
:::

### 3. Add the agent to its team and channel

The agent must be a member of every channel that the bridge serves. chitd
enforces channel authorization server-side. The hub only delivers events for
channels that the agent belongs to. A user added to an open or private channel must
be on the channel's team, so add it to the team first. Do this as a person who
is a member of the team (and, for a private channel, of the channel):

```bash
GW=http://localhost:4455
AUTH=(-H "X-Session-Token: $TOKEN")   # a team member's Kratos session token

AGENT_ID=$(curl -sS "${AUTH[@]}" "$GW/api/v1/users/username/claude-architect" | jq -r .id)

curl -sS "${AUTH[@]}" -X POST "$GW/api/v1/teams/$TEAM_ID/members" \
  -H 'Content-Type: application/json' -d "{\"user_id\":\"$AGENT_ID\"}"
curl -sS "${AUTH[@]}" -X POST "$GW/api/v1/channels/$CHANNEL_ID/members" \
  -H 'Content-Type: application/json' -d "{\"user_id\":\"$AGENT_ID\"}"
```

The UAT seeder already creates a `chit-agent` user with `actor_type=agent`,
membership in the UAT team and channel, and Kratos ID
`a9e47000-0000-4000-a000-000000000006`. The UAT stack runs no Hydra, so use it
with the trusted-proxy mode described below.

### 4. Authenticate the claude CLI

On a machine with a browser, generate a long-lived OAuth token and set it in
the bridge's environment:

```bash
claude setup-token          # requires a Pro/Max/Team/Enterprise subscription
export CLAUDE_CODE_OAUTH_TOKEN=<token>
```

:::caution[Subscription vs. API charges]
If `ANTHROPIC_API_KEY` is present in the bridge's environment, Claude Code
bills per-token against the API instead of the subscription. Keep it unset.
:::

### 5. Configure and run the bridge

```bash
# Point at Oathkeeper, not chitd — the token is only meaningful to the proxy
# that introspects it.
export CHIT_CLAUDE_SERVER_URL=http://localhost:4455
export CHIT_CLAUDE_OAUTH_TOKEN_URL=http://localhost:4444/oauth2/token
export CHIT_CLAUDE_OAUTH_CLIENT_ID=<hydra client id>
export CHIT_CLAUDE_OAUTH_CLIENT_SECRET=<hydra client secret>
export CHIT_CLAUDE_OAUTH_SCOPES="chit:read chit:write"
export CHIT_CLAUDE_OAUTH_AUDIENCE=chit

export CHIT_CLAUDE_CHANNELS=<channel-id>[,<channel-id>...]
export CHIT_CLAUDE_WORKDIR=/path/to/project    # where claude runs
# optional hardening / behavior:
export CHIT_CLAUDE_MODEL=claude-fable-5-1      # empty → the claude CLI default
export CHIT_CLAUDE_PERMISSION_MODE=dontAsk     # blocks tools not allowlisted
export CHIT_CLAUDE_ALLOWED_TOOLS="Read,Grep,Glob,Bash(go test *)"
export CHIT_CLAUDE_REQUIRE_MENTION=true        # the default; false → every post triggers a run
export CHIT_CLAUDE_RUN_TIMEOUT=30m

make build-claude
./bin/chit-claude
```

The full variable list is in `.env.example` (`CHIT_CLAUDE_*` block) and the
[configuration reference](/chit/reference/configuration/#chit-claude). Set
exactly one of `CHIT_CLAUDE_OAUTH_CLIENT_ID` (OAuth2 mode, which then also
requires the client secret and token URL) and `CHIT_CLAUDE_AGENT_KRATOS_ID`.
The bridge refuses to start with both, with neither, or with an incomplete
OAuth2 block. It does not select a mode for you.
`CHIT_CLAUDE_CHANNELS` and `CHIT_CLAUDE_WORKDIR` are always required. At
startup, the bridge checks that its agent is a member of every channel listed.
chitd only delivers posts to members. Without this check, a bridge could serve
a channel that its agent is not in, and never get a post from it. A refusal from
chitd (unknown channel, not a member) stops the bridge; a chitd that does not
answer only logs a warning.

The bridge caches tokens and renews them automatically. It fetches a new one
only when the current token expires (Hydra issues 1-hour tokens by default). If the
token endpoint is unreachable the request fails; it is never sent
unauthenticated, and the WebSocket reconnect loop backs off and retries.

:::note[Trusted-proxy mode]
`CHIT_CLAUDE_AGENT_KRATOS_ID` + `CHIT_CLAUDE_PROXY_SECRET` still work. They
point the bridge straight at chitd on `:8065`, around Oathkeeper. The bridge
sends the Kratos ID as `X-User-Id`. So the agent is a user with a Kratos ID
(such as UAT's `chit-agent`), not a declared machine actor. That path
asserts an identity but does not prove it. Its shared secret is the same
for every agent. So it cannot express per-agent or per-application privilege.
Keep it for local development; use OAuth2 anywhere else.
:::

## Talking to the agent

### When it answers

With the default `CHIT_CLAUDE_REQUIRE_MENTION=true`, the agent answers a post
that names it (`@claude-architect …`). After a post names it in a thread, later
replies in that thread need no mention. `CHIT_CLAUDE_FOLLOW_THREADS=true` (the
default) controls this, so a conversation reads naturally. Replies in threads
it has not joined, and every other post in the channel, cost nothing.

`@all` and `@channel` do not name the agent unless
`CHIT_CLAUDE_ANSWER_BROADCASTS=true`. If they did, one `@channel` could start a
run in every persona that serves the channel.

`CHIT_CLAUDE_REQUIRE_MENTION=false` answers every post in the channel,
side conversations between people included. That suits a channel where people only talk to one agent, and few others.

### What it sees

Each message reaches Claude tagged with its author: `[@alice] can you check
the migration?`. A session can start partway through a thread. For example,
a person names the agent in a conversation that already exists, or the bridge
replaces a lost session. Then the thread so far comes first, each post tagged
the same way. The bridge keeps the newest posts, up to
`CHIT_CLAUDE_SEED_MAX_CHARS` (default 8000; `0` turns it off). It includes the
agent's earlier replies without their footers.

### While it works

If a run continues after 10 seconds, the bridge shows `⏳ Working on it…` in
the thread. The bridge deletes the note when the reply arrives. The reply is
always a new post, so an `@mention` in it reaches other agents and notifies
people as usual. If a process kills the bridge mid-run (and does not stop it),
the note stays.

### Control words

Some messages to the agent (named, or in a thread it has joined) start with
one of these words. Such a message acts on the thread and does not go to Claude:

| Word | Effect |
|---|---|
| `!new` | The next message in this thread starts a new Claude session, with no earlier context. |
| `!new <message>` | Runs `<message>` in a new session. |
| `!stop` | Stops the run in progress and drops the thread's queued messages. |
| `!status` | Says whether a run is in progress (and for how long), how many messages are queued, and whether the next reply resumes a session. |

`!new` waits its turn in the thread's queue, so a run already under way
cannot undo it when it finishes. `!stop` and `!status` act at once.

## Multiple personas in one channel

**One bridge process serves exactly one agent user**: the one bound to its
OAuth2 client (or its `CHIT_CLAUDE_AGENT_KRATOS_ID`). The bridge resolves it
once at startup. You can run several personas, for example a `claude-architect`
on Fable 5 and a `claude-docs-writer` on Sonnet 5.5. To do this, run one
`chit-claude` process per persona. Give each its own Hydra client, agent user,
model, and work directory. They
can all serve the same channel.

### Provision the agent users

Per persona, create a Hydra client ([step 1](#1-give-the-agent-an-oauth2-client)),
then declare all of them in one `CHIT_MACHINE_ACTORS` value and restart chitd:

```bash
CHIT_MACHINE_ACTORS='[
  {"client_id": "<architect client_id>", "username": "claude-architect",
   "display_name": "Claude Architect", "actor_type": "agent"},
  {"client_id": "<docs-writer client_id>", "username": "claude-docs-writer",
   "display_name": "Claude Docs Writer", "actor_type": "agent"}
]'
```

Then add each one to the team and channel as in
[step 3](#3-add-the-agent-to-its-team-and-channel).

:::caution[Declare every persona as an agent]
The loop guard below resolves each post author's `actor_type`. **Every other
agent in the channel treats an agent user as a human if its type is not
`agent` or `bot`.** This defeats the guard for all of them.
`CHIT_MACHINE_ACTORS` refuses an entry without `actor_type`. So this problem
mostly affects agents created some other way. For example,
`POST /api/v1/users` (system-admin only) sets `actor_type` to `user` when the
body omits it.
The bridge logs a warning at startup when its own user is not
`actor_type=agent` — do not ignore it.
:::

### Loop prevention

Before these settings, the bridge's only built-in filter was "is this my own
post". So two bridges in one channel answered each other without end. Two
settings now control this:

| Variable | Default | Effect |
|---|---|---|
| `CHIT_CLAUDE_REPLY_TO_AGENTS` | `false` | Drop every post authored by an `agent` or `bot` actor. |
| `CHIT_CLAUDE_MAX_AGENT_HOPS` | `2` | Max consecutive agent→agent turns. Only read when `REPLY_TO_AGENTS=true`. |

With the default, agents never answer agents. This is safe, but only humans
can start their runs. Set `REPLY_TO_AGENTS=true` to let personas hand work to
each other. Then an agent answers an agent-authored post only when **all** of
these are true:

1. the content names this agent literally (`@claude-docs-writer`);
2. `@all` / `@channel` **does not count**. A broadcast is not an instruction
   to a specific agent. If it counted, one `@all` could restart an exchange;
3. the thread's hop count is below `MAX_AGENT_HOPS`.

Every agent reply carries a `claude_agent_hops` prop equal to its author's
count plus one. A post from a human carries no such prop. So **every human
turn resets the chain, and an A→B→A exchange stops after `MAX_AGENT_HOPS`
agent turns**. What the models write does not change this.

:::caution
`claude_agent_hops` is a post prop, so any client can write it. Trusted bridge processes use it to work together. It is not a security
boundary.
:::

`CHIT_CLAUDE_REQUIRE_MENTION` (see [how to talk to the
agent](#talking-to-the-agent)) is a separate gate. It applies to *all*
authors, humans too. The bridge always enforces the agent rules above
too.

### Per-persona configuration

Give each persona its own env file — `~/.config/chit-claude/architect.env`:

```bash
CHIT_CLAUDE_SERVER_URL=http://localhost:4455
CHIT_CLAUDE_OAUTH_TOKEN_URL=http://localhost:4444/oauth2/token
CHIT_CLAUDE_OAUTH_CLIENT_ID=<architect hydra client id>
CHIT_CLAUDE_OAUTH_CLIENT_SECRET=<architect hydra client secret>
CHIT_CLAUDE_OAUTH_SCOPES=chit:read chit:write
CHIT_CLAUDE_OAUTH_AUDIENCE=chit
CHIT_CLAUDE_CHANNELS=<shared channel id>
CHIT_CLAUDE_WORKDIR=/srv/worktrees/architect
CHIT_CLAUDE_MODEL=claude-fable-5-1
CHIT_CLAUDE_REQUIRE_MENTION=true
CHIT_CLAUDE_REPLY_TO_AGENTS=true
CHIT_CLAUDE_MAX_AGENT_HOPS=2
CLAUDE_CODE_OAUTH_TOKEN=...
```

`docs-writer.env` is the same with its **own** Hydra client, its own workdir,
and `CHIT_CLAUDE_MODEL=claude-sonnet-5-5`. One client per persona means tokens
are per-agent. If you revoke one agent's client, only that agent stops. The
audit trail tells the agents apart.

Two unrelated things here are both called an OAuth token:
`CHIT_CLAUDE_OAUTH_*` authenticates the bridge to Chit;
`CLAUDE_CODE_OAUTH_TOKEN` authenticates the `claude` CLI to Anthropic. Keep the
secret file mode `0600` — it holds both.

If the Anthropic subscription cannot serve the requested model, the `claude`
CLI exits non-zero and the bridge posts `⚠️ Claude run failed: …` into the
thread. The bridge reports the failure correctly. It is not a bug in the bridge.

### Supervising the processes

A systemd **user template** unit runs one instance per persona from one file —
`~/.config/systemd/user/chit-claude@.service`:

```ini
[Unit]
Description=chit-claude bridge (%i)
After=network-online.target

[Service]
Type=simple
EnvironmentFile=%h/.config/chit-claude/%i.env
ExecStart=%h/bin/chit-claude
Restart=on-failure
RestartSec=5s

# Stop waits up to CHIT_CLAUDE_SHUTDOWN_GRACE (60s) for runs in progress;
# keep TimeoutStopSec above it.
TimeoutStopSec=90s

[Install]
WantedBy=default.target
```

```bash
systemctl --user enable --now chit-claude@architect chit-claude@docs-writer
```

## Security notes

- **Access control is the channel allowlist.** Anyone who can post in a
  configured channel can drive Claude in the `WORKDIR`. Use a private
  channel: any *team* member may join an open channel, so "member of the
  channel" is trivially obtainable there.
- **`CHIT_CLAUDE_CHANNELS` is the boundary, not membership.** The operator
  does not control channel membership. Any team member can add the agent to
  an open channel. A new open channel auto-adds every team member, the agent
  too. Any user can open a DM or group channel with the agent. The bridge
  drops those posts because the channel is not on the allowlist. It logs a
  warning **once per channel** when it sees one:

  ```
  WARN ignoring post from a channel outside CHIT_CLAUDE_CHANNELS;
       this agent is a member of a channel it does not serve channel_id=...
  ```

  That line means that someone pulled the agent into a channel that you did
  not intend. Send an alert when it occurs.
- **The agent must be on the team, so keep the team small.** A user added to
  an open or private channel must be on the channel's team. So the agent can
  be in a team channel only if it is on the team. On the team, chitd auto-adds
  it to every open channel created there. If you remove the agent from the
  team, chitd removes it from all of the team's channels.
- **Watch who joins the channel.** Any member of a private channel may invite
  anyone on the team. But to remove another user, a user must have
  `system_admin`. It is easier to add to the member list than to remove from
  it, and that list is the real trust boundary.
- **Prompts go in on stdin.** Message content reaches the claude binary on
  its standard input, never through a shell and never in its arguments.
  (When the prompt went in as an argument, the CLI parsed a post with the
  text `--version` as that option. The reason: `-p` is a flag, and the prompt
  is the CLI's positional argument.)
- **The host's Claude Code setup stays out.** Runs pass
  `--strict-mcp-config` and `--setting-sources project`, so MCP servers,
  permissions, hooks and plugins configured for the host user do not reach
  the agent. Set `CHIT_CLAUDE_SETTING_SOURCES=all` only if you want them to.
- **Anyone who can address the agent can steer the thread.** That includes
  the [control words](#control-words): `!stop` and `!new` from any channel
  member who names the agent, or replies in a thread it has joined.
- **The gateway now enforces, and it is no longer optional.** The API access
  rules previously listed `noop` as a fallback authenticator. So an
  unauthenticated request passed Oathkeeper, and only chitd rejected it.
  That fallback is gone from `deploy/chit.kube.yml` (the UAT manifest still
  has it). Each request to `/api/v1/**` must present a credential. This
  includes the unauthenticated chitd routes such as `/system/ping`. The
  credential is a Kratos session token, or a Hydra access token with audience
  `chit` and the scope that its method requires. Keep `CHIT_TRUSTED_PROXY_SECRET` set so the
  backend still refuses anything that did not come through the proxy.
- **Constrain the tools.** `PERMISSION_MODE=dontAsk` plus a tight
  `ALLOWED_TOOLS` list is the safe default for unattended runs; widen it
  deliberately per project.
- **One workdir per persona when you allow write tools.** With the default
  read-only `ALLOWED_TOOLS`, a shared `WORKDIR` is harmless. But when you
  enable `Edit`/`Write`/`Bash`, two personas in one checkout overwrite each
  other's changes mid-run. A `git worktree` per persona is the cheap fix and gives
  each one its own branch.

## Operations

### Limits

| What | Limit | What happens past it |
|---|---|---|
| Runs at once, across threads | `CHIT_CLAUDE_MAX_CONCURRENT_RUNS` (2) | Further runs wait for a slot. |
| Messages queued per thread | 16 | The thread is told once that a message was dropped and should be resent. |
| One run | `CHIT_CLAUDE_RUN_TIMEOUT` (30m) | The run is killed and the thread told. |
| One reply | 64 KiB, chitd's post limit | The reply is split across several posts. |

### Sessions live in `~/.claude`, under the working directory

Claude Code keeps each session's transcript under `~/.claude/projects/`, keyed
by the directory it ran in. The thread only stores the session's ID. If
`CHIT_CLAUDE_WORKDIR` changes, or the bridge's home is not persistent (a
container without a volume for it), the bridge cannot resume a thread's session. The
bridge then starts a new session for that thread, seeded with the thread so
far, and says so in the reply. Persist `~/.claude` to avoid it.

### Restarts and shutdown

On `SIGTERM` or `SIGINT` the bridge stops and accepts no new events. It lets
runs in progress finish for up to `CHIT_CLAUDE_SHUTDOWN_GRACE` (60s). Then it
stops the rest and says so in their threads. If a thread has queued messages
that never started, the bridge tells that thread once to send them again. Keep the supervisor's stop timeout above the
grace period (systemd's `TimeoutStopSec` defaults to 90s).

A thread idle for 10 minutes frees its worker. When the thread gets its next
message, the bridge recovers the session from the thread's posts, as after a
restart.

### Logs

The bridge logs JSON to stderr. Each run writes one `run_complete` line:

```json
{"level":"INFO","msg":"run_complete","root_id":"…","post_id":"…","resumed":true,
 "duration_ms":48210,"ok":true,"input_tokens":12,"output_tokens":1840,
 "cache_read_tokens":61204,"cache_write_tokens":3310,"context_tokens":64526,
 "cost_usd":0.21,"num_turns":4}
```

Add these up to get the totals per thread, per persona or per day. `context_tokens` is
the size of the conversation after the run.

## Token cost

**The bridge adds almost nothing to a turn.** Claude receives the message
text with an author tag of a few tokens. `--resume` reloads the same
transcript that an interactive session reloads. A fresh session starts with Claude
Code's own system prompt and tool definitions, about 21k tokens with the
default tools (measured with `claude` 2.1.292). That is the same with or
without the bridge.

What decides the cost is **how many runs happen and how long each session
gets**:

- **Which posts start a run.** With the default gate, only posts that name
  the agent, and replies in threads it has joined, do. With
  `REQUIRE_MENTION=false`, every post in the channel does, once for each
  persona that serves it.
- **Cold caches.** Each resumed turn re-reads the whole conversation. Within
  the prompt cache's lifetime that is cheap (a cache read). After it lapses,
  the next turn writes the whole conversation into the cache again, at more
  than the price of plain input. The footer shows cache **reads** and
  **writes** separately; a long thread with many writes is the expensive
  case. The `claude` 2.1.292 CLI wrote its cache entries with a 1-hour
  lifetime.
- **Session size.** A thread's session grows with every turn, and each turn
  re-reads all of it. `CHIT_CLAUDE_MAX_SESSION_TOKENS`
  retires a session when its context reaches that many tokens. The reply says
  so. The next message starts a new session, without the old context
  (restate what matters). `!new` does the same on demand.
- **What runs load.** Runs load no MCP servers and none of the host user's
  settings unless configured to. If you attach `chit-mcp`, it adds its tool
  definitions to every turn, and whatever its tools return to the
  conversation. Its tools return posts as id, author, content and time only,
  without props.

To compare the bridge against plain `claude -p --resume` on a local setup,
run `scripts/bridge-token-baseline.sh`.

## The footer

Each reply ends with a token and cost line built from the run's JSON result.
It needs no OpenTelemetry collector:

```
⚙ in 12 · out 1.8k · cache read 61.2k · write 3.3k · $0.21 · context ~32%
```

`in`, `out`, `cache read` and `write` are the run's totals over every API call
it made. `context ~N%` is the conversation's size after the run, divided by the
model's context window. The size is everything the last API call read: input,
cache reads and cache writes. The context window is the value that the CLI
reports. If the CLI reports none, the bridge uses `CHIT_CLAUDE_CONTEXT_WINDOW`
(default 200000). For subscription (OAuth) runs, the `$` figure is the price
of the run at API rates. The subscription does not charge this amount. `CHIT_CLAUDE_FOOTER=false` drops the line; the same figures stay in
the reply's `claude_usage` prop. If you later want time-series dashboards,
Claude Code's OpenTelemetry support (`CLAUDE_CODE_ENABLE_TELEMETRY=1`) can run
alongside this unchanged.
