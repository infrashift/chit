---
title: Headless Claude Code
description: Drive headless Claude Code sessions from Chit channels with the chit-claude bridge.
---

The `chit-claude` bridge turns Chit into an asynchronous, markdown-native
front-end for [Claude Code](https://code.claude.com/docs). Post a message in a
configured channel and the bridge runs `claude -p` headlessly in a working
directory of your choice; Claude's response lands back in the thread as the
agent user, with a token/cost footer. Replying in the thread resumes the same
Claude session — full context intact — so a task can span hours or days with
no terminal open anywhere.

## How it works

```
you (any Chit client)
   │  post "plan the migration of service X"
   ▼
chitd ──WebSocket (posted event)──▶ chit-claude bridge
                                        │ claude -p "<message>" --output-format json
                                        │ (adds --resume <session_id> on thread replies)
                                        ▼
                                    claude CLI ──▶ Anthropic (subscription OAuth)
                                        │ result JSON: text + session_id + usage
                                        ▼
chitd ◀──REST POST /posts (threaded reply + footer + session prop)──┘
```

- **Thread = session.** A root post starts a new Claude session. The bridge
  stores the returned `session_id` in the agent reply's `props`
  (`claude_session_id`), so state lives in the conversation itself and
  survives bridge restarts. Replies in the thread run
  `claude -p --resume <session_id>`.
- **One run at a time per thread.** Messages arriving while Claude is working
  queue up in order (resuming the same session from two processes at once
  would interleave its transcript).
- **The runner posts the reply.** Claude runs with no MCP servers attached in
  this setup; the bridge captures the `--output-format json` result and posts
  it. Attaching `chit-mcp` via `--mcp-config` so Claude can post mid-run
  updates itself is possible but optional.
- **Failures are visible.** A failed or timed-out run posts an error reply
  (with the stderr tail) to the thread instead of going silent.

:::caution[Session resumption gotcha]
`claude -p --session-id <id>` does **not** resume a session on later runs —
that flag assigns an ID to a *new* session. Resumption is
`claude -p --resume <session_id>`, using the `session_id` captured from the
previous run's JSON output. The bridge handles this for you; the note is here
because most hand-rolled scripts get it wrong.
:::

## Setup

### 1. Give the agent an OAuth2 client

Agents authenticate to Chit with an Ory Hydra access token obtained through the
`client_credentials` grant, presented to Oathkeeper, which introspects it and
enforces the token's audience and scope before forwarding anything to chitd
with the token's `client_id` in `X-Client-Id`.

Create the client in Hydra (the `make kube-up` stack runs it, admin API on
`:4445`):

```bash
HYDRA_ADMIN=http://localhost:4445

# Hydra generates the client_id and secret. Note both — the secret is
# shown once.
curl -sS -X POST "$HYDRA_ADMIN/admin/clients" \
  -H 'Content-Type: application/json' -d '{
    "client_name":                "claude-architect",
    "grant_types":                ["client_credentials"],
    "token_endpoint_auth_method": "client_secret_post",
    "scope":                      "chit:read chit:write",
    "audience":                   ["chit"]
  }'
```

Either `client_secret_post` or `client_secret_basic` works — Hydra enforces
whichever the client registered and rejects the other with `invalid_client`,
so the bridge auto-detects rather than pinning one.

**Scopes.** `chit:read` covers every `GET` (including the WebSocket upgrade);
`chit:write` covers `POST`/`PUT`/`DELETE`. The bridge needs both: it listens
over the WebSocket and posts replies. Note that Chit's search and batch-tag
endpoints are `POST`s despite only reading, so they fall under `chit:write`
too — a strictly read-only token can list and fetch but cannot search.

**Audience.** `chit` is what isolates applications sharing the gateway: a token
minted for another audience is rejected by Oathkeeper's rules even though it is
a perfectly valid Hydra token.

### 2. Declare the agent user

A machine actor has no Kratos identity and no email, and chitd never creates
its user on first use: a token for a client chitd does not know is answered
401.
Declare the agent in chitd's environment with `CHIT_MACHINE_ACTORS`, a JSON
array with one entry per client:

```bash
CHIT_MACHINE_ACTORS='[
  {"client_id": "<client_id from step 1>", "username": "claude-architect",
   "display_name": "Claude Architect", "actor_type": "agent"}
]'
```

`actor_type` is required and must be `agent` for a bridge persona (`bot` is
the other accepted value). `roles` is optional, space-separated, and
defaults to `system_user`; `system_admin` is a real grant, so leave it out
unless the agent needs it. See the
[configuration reference](/chit/reference/configuration/#machine-actors) for
every field.

chitd reconciles the list at every boot, before it accepts requests: it
creates each actor that is missing and updates `username`, `display_name`,
`roles` and `actor_type` to match the declaration, so an edit takes effect on
the next restart. Removing an entry does not delete the user. An invalid entry
stops chitd from starting.

In the `make kube-up` stack, chitd's environment is the `chitd` container in
`deploy/chit.kube.yml`: add `CHIT_MACHINE_ACTORS` to its `env` and run
`make kube-restart`, or run chitd yourself with `make run` and set it in
`.env`.

:::caution[The binding is the identity]
For the `client_credentials` grant Hydra sets the token's `sub` to the
generated `client_id`, and does **not** expose client metadata through token
introspection. Chit therefore resolves the client against
`users.oauth_client_id`, which is the declaration's `client_id`. A client
with no binding is rejected outright — unlike an unknown Kratos ID, it is
never provisioned into a new user.
:::

### 3. Add the agent to its team and channel

The agent must be a member of every channel the bridge should serve: channel
authorization is enforced server-side, and the hub only delivers events for
channels the agent belongs to. A user added to an open or private channel must
be on the channel's team, so add it to the team first. Do this as a person who
is a member of the team (and, for a private channel, of the channel):

```bash
GW=http://localhost:4455
AUTH=(-H "X-Session-Token: $TOKEN")   # a team member's Kratos session token

AGENT_ID=$(curl -sS "${AUTH[@]}" "$GW/api/v1/users/username/claude-architect" | jq -r .id)

curl -sS "${AUTH[@]}" -X POST "$GW/api/v1/teams/$TEAM_ID/members" \
  -H 'Content-Type: application/json' -d "{\"user_id\":\"$AGENT_ID\"}"
curl -sS "${AUTH[@]}" -X POST "$GW/api/v1/channels/$CHANNEL_ID/members" \
  -H 'Content-Type: application/json' -d "{\"user_id\":\"$AGENT_ID\"}"
```

The UAT seeder already creates a `chit-agent` user with `actor_type=agent`,
membership in the UAT team and channel, and Kratos ID
`a9e47000-0000-4000-a000-000000000006`. The UAT stack runs no Hydra, so use it
with the trusted-proxy mode described below.

### 4. Authenticate the claude CLI

On a machine with a browser, generate a long-lived OAuth token and set it in
the bridge's environment:

```bash
claude setup-token          # requires a Pro/Max/Team/Enterprise subscription
export CLAUDE_CODE_OAUTH_TOKEN=<token>
```

:::caution[Subscription vs. API billing]
If `ANTHROPIC_API_KEY` is present in the bridge's environment, Claude Code
bills per-token against the API instead of your subscription. Keep it unset.
:::

### 5. Configure and run the bridge

```bash
# Point at Oathkeeper, not chitd — the token is only meaningful to the proxy
# that introspects it.
export CHIT_CLAUDE_SERVER_URL=http://localhost:4455
export CHIT_CLAUDE_OAUTH_TOKEN_URL=http://localhost:4444/oauth2/token
export CHIT_CLAUDE_OAUTH_CLIENT_ID=<hydra client id>
export CHIT_CLAUDE_OAUTH_CLIENT_SECRET=<hydra client secret>
export CHIT_CLAUDE_OAUTH_SCOPES="chit:read chit:write"
export CHIT_CLAUDE_OAUTH_AUDIENCE=chit

export CHIT_CLAUDE_CHANNELS=<channel-id>[,<channel-id>...]
export CHIT_CLAUDE_WORKDIR=/path/to/project    # where claude runs
# optional hardening / behavior:
export CHIT_CLAUDE_MODEL=claude-fable-5        # empty → the claude CLI default
export CHIT_CLAUDE_PERMISSION_MODE=dontAsk     # blocks tools not allowlisted
export CHIT_CLAUDE_ALLOWED_TOOLS="Read,Grep,Glob,Bash(go test *)"
export CHIT_CLAUDE_REQUIRE_MENTION=false       # true → only @chit-agent posts trigger runs
export CHIT_CLAUDE_RUN_TIMEOUT=30m

make build-claude
./bin/chit-claude
```

The full variable list is in `.env.example` (`CHIT_CLAUDE_*` block) and the
[configuration reference](/chit/reference/configuration/#chit-claude). Setting
`CHIT_CLAUDE_OAUTH_CLIENT_ID` selects OAuth2 mode, and the bridge then refuses
to start without the client secret and token URL rather than falling back to
the weaker mode; without it, `CHIT_CLAUDE_AGENT_KRATOS_ID` is required.
`CHIT_CLAUDE_CHANNELS` and `CHIT_CLAUDE_WORKDIR` are always required.

Tokens are cached and renewed automatically — the bridge fetches a new one only
when the current token expires (Hydra issues 1-hour tokens by default). If the
token endpoint is unreachable the request fails; it is never sent
unauthenticated, and the WebSocket reconnect loop backs off and retries.

:::note[Trusted-proxy mode]
`CHIT_CLAUDE_AGENT_KRATOS_ID` + `CHIT_CLAUDE_PROXY_SECRET` still work, pointing
the bridge straight at chitd on `:8065` and bypassing Oathkeeper. The bridge
sends the Kratos ID as `X-User-Id`, so the agent is a user with a Kratos ID
(such as UAT's `chit-agent`), not a declared machine actor. That path
asserts an identity rather than proving one, and its shared secret is the same
for every agent, so it cannot express per-agent or per-application privilege.
Keep it for local development; use OAuth2 anywhere else.
:::

## Multiple personas in one channel

**One bridge process serves exactly one agent user**: the one bound to its
OAuth2 client (or its `CHIT_CLAUDE_AGENT_KRATOS_ID`), resolved once at
startup. To run several personas — say a `claude-architect` on Fable 5 and a
`claude-docs-writer` on Sonnet — run one `chit-claude` process per persona,
each with its own Hydra client, agent user, model, and working directory. They
can all serve the same channel.

### Provision the agent users

Per persona, create a Hydra client ([step 1](#1-give-the-agent-an-oauth2-client)),
then declare all of them in one `CHIT_MACHINE_ACTORS` value and restart chitd:

```bash
CHIT_MACHINE_ACTORS='[
  {"client_id": "<architect client_id>", "username": "claude-architect",
   "display_name": "Claude Architect", "actor_type": "agent"},
  {"client_id": "<docs-writer client_id>", "username": "claude-docs-writer",
   "display_name": "Claude Docs Writer", "actor_type": "agent"}
]'
```

Then add each one to the team and channel as in
[step 3](#3-add-the-agent-to-its-team-and-channel).

:::caution[Declare every persona as an agent]
The loop guard below works by resolving each post author's `actor_type`.
**An agent user typed as anything other than `agent` or `bot` is treated as a
human by every other agent in the channel**, which defeats the guard for all of
them. `CHIT_MACHINE_ACTORS` refuses an entry without `actor_type`, so this
mostly bites agents created some other way (`POST /api/v1/users`, which is
system-admin only, defaults `actor_type` to `user` when the body omits it).
The bridge logs a warning at startup when its own user is not
`actor_type=agent` — do not ignore it.
:::

### Loop prevention

The bridge's only built-in filter used to be "is this my own post", so two
bridges in one channel would answer each other indefinitely. Two settings now
govern this:

| Variable | Default | Effect |
|---|---|---|
| `CHIT_CLAUDE_REPLY_TO_AGENTS` | `false` | Drop every post authored by an `agent` or `bot` actor. |
| `CHIT_CLAUDE_MAX_AGENT_HOPS` | `2` | Max consecutive agent→agent turns. Only read when `REPLY_TO_AGENTS=true`. |

With the default, agents never answer agents — safe, but they can only be
driven by humans. Set `REPLY_TO_AGENTS=true` to let personas hand work to each
other. An agent-authored post is then answered only when **all** of:

1. the content names this agent literally (`@claude-docs-writer`);
2. `@all` / `@channel` **does not count** — a broadcast is not an instruction
   to a specific agent, and counting it would let one `@all` restart an
   exchange;
3. the thread's hop count is below `MAX_AGENT_HOPS`.

Every agent reply carries a `claude_agent_hops` prop equal to its author's
count plus one, and a post from a human carries no such prop — so **every human
turn resets the chain, and an A→B→A exchange stops after `MAX_AGENT_HOPS`
agent turns** regardless of what the models write.

:::caution
`claude_agent_hops` is a post prop, so any client can write it. This is a
cooperation mechanism between trusted bridge processes, not a security
boundary.
:::

Note that `CHIT_CLAUDE_REQUIRE_MENTION` is a separate, coarser gate that
applies to *all* authors including humans. The agent rules above are always
enforced on top of it.

### Per-persona configuration

Give each persona its own env file — `~/.config/chit-claude/architect.env`:

```bash
CHIT_CLAUDE_SERVER_URL=http://localhost:4455
CHIT_CLAUDE_OAUTH_TOKEN_URL=http://localhost:4444/oauth2/token
CHIT_CLAUDE_OAUTH_CLIENT_ID=<architect hydra client id>
CHIT_CLAUDE_OAUTH_CLIENT_SECRET=<architect hydra client secret>
CHIT_CLAUDE_OAUTH_SCOPES=chit:read chit:write
CHIT_CLAUDE_OAUTH_AUDIENCE=chit
CHIT_CLAUDE_CHANNELS=<shared channel id>
CHIT_CLAUDE_WORKDIR=/srv/worktrees/architect
CHIT_CLAUDE_MODEL=claude-fable-5
CHIT_CLAUDE_REQUIRE_MENTION=true
CHIT_CLAUDE_REPLY_TO_AGENTS=true
CHIT_CLAUDE_MAX_AGENT_HOPS=2
CLAUDE_CODE_OAUTH_TOKEN=...
```

`docs-writer.env` is the same with its **own** Hydra client, its own workdir,
and `CHIT_CLAUDE_MODEL=claude-sonnet-5`. One client per persona means tokens
are per-agent: revoking one agent's client stops that agent alone, and the
audit trail distinguishes them.

Two unrelated things here are both called an OAuth token:
`CHIT_CLAUDE_OAUTH_*` authenticates the bridge to Chit;
`CLAUDE_CODE_OAUTH_TOKEN` authenticates the `claude` CLI to Anthropic. Keep the
secret file mode `0600` — it holds both.

If the Anthropic subscription cannot serve the requested model, the `claude`
CLI exits non-zero and the bridge posts `⚠️ Claude run failed: …` into the
thread. That is the bridge reporting faithfully, not a bug in it.

### Supervising the processes

A systemd **user template** unit runs one instance per persona from one file —
`~/.config/systemd/user/chit-claude@.service`:

```ini
[Unit]
Description=chit-claude bridge (%i)
After=network-online.target

[Service]
Type=simple
EnvironmentFile=%h/.config/chit-claude/%i.env
ExecStart=%h/bin/chit-claude
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=default.target
```

```bash
systemctl --user enable --now chit-claude@architect chit-claude@docs-writer
```

## Security notes

- **Access control is the channel allowlist.** Anyone who can post in a
  configured channel can drive Claude in your `WORKDIR`. Use a private
  channel: any *team* member may join an open channel, so "member of the
  channel" is trivially obtainable there.
- **`CHIT_CLAUDE_CHANNELS` is the boundary, not membership.** Channel
  membership is not under your control — any team member can add the agent to
  an open channel, creating an open channel auto-adds every team member
  including the agent, and any user can open a DM or group channel with it.
  Those posts are dropped because the channel is not on the allowlist, and the
  bridge logs a warning **once per channel** when it sees one:

  ```
  WARN ignoring post from a channel outside CHIT_CLAUDE_CHANNELS;
       this agent is a member of a channel it does not serve channel_id=...
  ```

  Treat that line as a signal that someone pulled your agent somewhere you did
  not intend. Alert on it.
- **Team membership is required, so keep the team small.** A user added to an
  open or private channel must be on the channel's team, so the agent cannot
  be in a team channel without being on the team — and on the team, it is
  auto-added to every open channel created there. Removing the agent from the
  team removes it from all of the team's channels.
- **Watch who joins the channel.** Any member of a private channel may invite
  anyone on the team, while removing somebody else requires `system_admin`.
  The member list is easier to grow than to shrink, and it is your real trust
  boundary.
- **Prompts are argv, never shell.** Message content is passed to the claude
  binary as a process argument; there is no shell interpolation to inject
  into.
- **The gateway now enforces, and it is no longer optional.** The API access
  rules previously listed `noop` as a fallback authenticator, so an
  unauthenticated request passed Oathkeeper and was rejected only by chitd.
  That fallback is gone from `deploy/chit.kube.yml` (the UAT manifest still
  has it): a request to `/api/v1/**`, the unauthenticated chitd routes such as
  `/system/ping` included, must present either a Kratos session token or a
  Hydra access token with audience `chit` and the scope its method requires. Keep `CHIT_TRUSTED_PROXY_SECRET` set so the
  backend still refuses anything that did not come through the proxy.
- **Constrain the tools.** `PERMISSION_MODE=dontAsk` plus a tight
  `ALLOWED_TOOLS` list is the safe default for unattended runs; widen it
  deliberately per project.
- **One workdir per persona once write tools are allowed.** With the default
  read-only `ALLOWED_TOOLS` a shared `WORKDIR` is harmless, but as soon as
  `Edit`/`Write`/`Bash` is enabled, two personas in one checkout will clobber
  each other mid-run. A `git worktree` per persona is the cheap fix and gives
  each one its own branch.

## The footer

Each reply ends with a usage line built from the run's JSON result — no
OpenTelemetry collector required:

```
⚙ tokens in 4.5k · out 1.2k · cache 38.0k · $0.42 · context ~21%
```

`context ~N%` estimates window fill as
`(cache_read_input_tokens + input_tokens) / CHIT_CLAUDE_CONTEXT_WINDOW`
(default 200000). For subscription (OAuth) runs the `$` figure is what the
run *would have cost* on the API, not an actual charge. If you later want
time-series dashboards, Claude Code's OpenTelemetry support
(`CLAUDE_CODE_ENABLE_TELEMETRY=1`) can run alongside this unchanged.
