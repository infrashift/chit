Chit delegates identity, authentication, and authorization to the
[Ory](https://www.ory.sh/) open-source stack. This provides zero-trust
security without embedding auth logic in the application.

## Components

| Component | Version | Role | Port(s) |
|---|---|---|---|
| **Kratos** | v1.3 | Identity management for people (registration, login, sessions) | 4433 (public), 4434 (admin) |
| **Hydra** | v2.2 | OAuth2 server; issues `client_credentials` tokens to machine actors | 4444 (public), 4445 (admin) |
| **Oathkeeper** | v0.40 | Authentication proxy (validates sessions and tokens, forwards identity) | 4455 (proxy), 4456 (API) |
| **Keto** | v0.12 | Authorization engine for slash commands | 4466 (read), 4467 (write) |

## Authentication Flow

In `deploy/chit.kube.yml`, every request to `/api/v1/**` through Oathkeeper
must carry one of two credentials. There is no anonymous rule: even
`/system/ping`, `/system/config/client` and `/docs` answer 401 through the
gateway without one, although chitd serves them without authentication when
called directly.

```
Person:  X-Session-Token ──► Oathkeeper ──► Kratos /sessions/whoami
                                 │
                                 └──► chitd   X-User-Id: <kratos identity id>

Machine: Authorization: Bearer <token> ──► Oathkeeper ──► Hydra introspection
                                               │          (audience, scope)
                                               └──► chitd   X-Client-Id: <client_id>
```

**People** (the `bearer_token` authenticator):

1. The client obtains a session token from a Kratos login flow and sends it in
   `X-Session-Token`
2. Oathkeeper validates it with Kratos (`/sessions/whoami`)
3. Oathkeeper forwards the request with the Kratos identity ID in `X-User-Id`
4. chitd reads `X-User-Id` (`CHIT_TRUSTED_PROXY_HEADER`) and provisions the
   user if needed (below)

**Machine actors** (the `oauth2_introspection` authenticator):

1. The agent or bot obtains an access token from Hydra with the
   `client_credentials` grant and sends it as `Authorization: Bearer`
2. Oathkeeper introspects it with Hydra's admin API and requires audience
   `chit` plus scope `chit:read` (for `GET`) or `chit:write` (for `POST`, `PUT`
   and `DELETE`)
3. Oathkeeper forwards the request with the token's subject, which is the
   `client_id` for this grant, in `X-Client-Id`
4. chitd reads `X-Client-Id` (`CHIT_TRUSTED_CLIENT_HEADER`) and resolves it to
   the user bound to that client. An unknown client gets 401; it is never
   created on the fly. Machine actors are declared with `CHIT_MACHINE_ACTORS`
   (see the [configuration reference](/chit/reference/configuration/#machine-actors)).

Oathkeeper's header mutator sets exactly one of the two headers per request and
blanks the other, so a client cannot smuggle its own. chitd checks
`X-Client-Id` first. Set `CHIT_TRUSTED_PROXY_SECRET` on chitd and the matching
`X-Proxy-Secret` header in the mutator so chitd also refuses requests that did
not come through Oathkeeper.

Kratos self-service endpoints are exposed anonymously through the gateway at
`http://localhost:4455/kratos/...`, which is how a person obtains a session
token.

The [UAT environment](/chit/getting-started/manual-acceptance-testing/)
(`deploy/chit-uat.kube.yml`) is looser: it runs no Hydra, accepts only Kratos
session tokens, and keeps an anonymous `noop` fallback on `/api/v1/**`, so a
request without a token reaches chitd and chitd's own authentication decides.

## User Auto-Provisioning

This applies to people only. Chit does **not** use Kratos webhooks to create
local user records. Instead, on the first authenticated request from a new
identity:

1. Chit receives the `X-User-Id` header from Oathkeeper
2. The App layer checks if a local user exists for this Kratos ID
3. If not found, it fetches the identity from the Kratos Admin API
   (`CHIT_KRATOS_ADMIN_URL`)
4. A local `users` record is created with the identity's traits (username,
   display name, email)

This approach avoids webhook configuration complexity and ensures the local
user record is always created in the context of a valid request.

## Keto Authorization (ReBAC)

Chit uses two Keto namespaces:

| Namespace | Relation | Meaning |
|---|---|---|
| `chit/command` | `execute` | Actor may execute a slash command |
| `chit/channel` | `member` | Mirror of channel membership; not used for access checks |

### Permission Checks

Slash-command execution is the only thing Keto authorizes: the
`chit/command` namespace uses the `execute` relation, granted via roles
defined in CUE under `auth/` and pushed into Keto by the `chit-reconcile`
binary. The caller must also be a member of the channel the command is run
in.

Channel access checks (read, post, pin, invite) use the PostgreSQL
`channel_members` table and nothing else. chitd never queries the
`chit/channel` namespace.

### Relationship Management

chitd mirrors channel membership into `chit/channel` on a best-effort basis: a
failed Keto write does not fail the request and is not retried.

- **Join channel:** Create `chit/channel:{channel_id}#member@{user_id}`
- **Leave channel, or leave the team that owns it:** Delete
  `chit/channel:{channel_id}#member@{user_id}`

Members added when a channel is created (the creator, every team member of a
new open channel, the participants of a DM or group channel) are written in
the background, after the response, so the tuples can appear a moment later.

## Config File References

Ory configuration files are embedded in the Podman Kube manifest as
ConfigMaps:

| File | ConfigMap | Description |
|---|---|---|
| Kratos config | `chit-kratos-config` | Server settings, self-service flows, identity schema |
| Hydra config | `chit-hydra-config` | Ports, issuer URL, opaque 1-hour access tokens, system secret |
| Oathkeeper config | `chit-oathkeeper-config` | Access rules, authenticators, authorizers, mutators |
| Keto config | `chit-keto-config` | Namespace definitions and server settings |

The database DSNs are passed to each service as the `DSN` environment
variable in the pod spec. The Hydra system secret in the manifest is a
placeholder; change it for anything but local development.

See `deploy/chit.kube.yml` for the full configuration, and the `deploy/`
directory for standalone reference copies.
