Chit delegates identity, authentication, and authorization to the
[Ory](https://www.ory.sh/) open-source stack. This gives zero-trust
security, and the application contains no auth logic of its own.

## Components

| Component | Version | Role | Port(s) |
|---|---|---|---|
| **Kratos** | v26.2.0 | Identity management for people (registration, login, sessions) | 4433 (public), 4434 (admin) |
| **Hydra** | v26.2.0 | OAuth2 server; issues `client_credentials` tokens to machine actors | 4444 (public), 4445 (admin) |
| **Oathkeeper** | v26.2.0 | Authentication proxy (validates sessions and tokens, forwards identity) | 4455 (proxy), 4456 (API) |
| **Keto** | keto-cue `809351b3` | Authorization engine for slash commands ([keto-cue](https://github.com/infrashift/keto-cue): Keto with CUE permission schemas) | 4466 (read), 4467 (write) |

## Authentication Flow

In `deploy/chit.kube.yml`, every request to `/api/v1/**` through Oathkeeper
must carry one of two credentials. There is no anonymous rule. Even
`/system/ping`, `/system/config/client` and `/docs` answer 401 through the
gateway without a credential. chitd serves them without authentication when
a client calls chitd directly.

```
Person:  X-Session-Token ──► Oathkeeper ──► Kratos /sessions/whoami
                                 │
                                 └──► chitd   X-User-Id: <kratos identity id>

Machine: Authorization: Bearer <token> ──► Oathkeeper ──► Hydra introspection
                                               │          (audience, scope)
                                               └──► chitd   X-Client-Id: <client_id>
```

**People** (the `bearer_token` authenticator):

1. The client obtains a session token from a Kratos login flow and sends it in
   `X-Session-Token`
2. Oathkeeper validates it with Kratos (`/sessions/whoami`)
3. Oathkeeper forwards the request with the Kratos identity ID in `X-User-Id`
4. chitd reads `X-User-Id` (`CHIT_TRUSTED_PROXY_HEADER`) and provisions the
   user if needed (below)

**Machine actors** (the `oauth2_introspection` authenticator):

1. The agent or bot obtains an access token from Hydra with the
   `client_credentials` grant and sends it as `Authorization: Bearer`
2. Oathkeeper introspects it with Hydra's admin API. The token must have
   audience `chit` plus scope `chit:read` (for `GET`) or `chit:write` (for
   `POST`, `PUT` and `DELETE`)
3. Oathkeeper forwards the request with the token's subject, which is the
   `client_id` for this grant, in `X-Client-Id`
4. chitd reads `X-Client-Id` (`CHIT_TRUSTED_CLIENT_HEADER`) and resolves it to
   the user bound to that client. An unknown client gets 401; it is never
   created on the fly. The operator declares machine actors with `CHIT_MACHINE_ACTORS`
   (see the [configuration reference](/chit/reference/configuration/#machine-actors)).

Oathkeeper's header mutator sets exactly one of the two headers per request and
blanks the other, so a client cannot smuggle its own. chitd checks
`X-Client-Id` first. Set `CHIT_TRUSTED_PROXY_SECRET` on chitd and the same value in the
`X-Proxy-Secret` header in the mutator. Then chitd also refuses requests that did
not come through Oathkeeper.

The gateway exposes the Kratos self-service endpoints anonymously at
`http://localhost:4455/kratos/...`. A person obtains a session token through
these endpoints.

The [UAT environment](/chit/getting-started/manual-acceptance-testing/)
(`deploy/chit-uat.kube.yml`) is looser. It runs no Hydra and accepts only Kratos
session tokens. It keeps an anonymous `noop` fallback on `/api/v1/**`. So a
request without a token reaches chitd, and chitd's own authentication decides.

## User Auto-Provisioning

This applies to people only. Chit does **not** use Kratos webhooks to create
local user records. Instead, on the first authenticated request from a new
identity:

1. Chit receives the `X-User-Id` header from Oathkeeper
2. The App layer checks if a local user exists for this Kratos ID
3. If not found, it fetches the identity from the Kratos Admin API
   (`CHIT_KRATOS_ADMIN_URL`)
4. It creates a local `users` record with the identity's traits (username,
   display name, email)

This approach avoids webhook configuration complexity and ensures the local
user record is always created in the context of a valid request.

## Keto Authorization (ReBAC)

Chit uses two Keto namespaces. Chit's file of the keto-cue schema directory,
`deploy/keto/schema/chit.cue`, declares them. A third, `chit/actor`, only names
the subject type of the IDs Chit writes:

| Namespace | Relation | Meaning |
|---|---|---|
| `chit/command` | `execute` | Actor may execute a slash command |
| `chit/channel` | `member` | Mirror of channel membership; not used for access checks |

### Permission Schema

keto-cue reads the schema from `namespaces.location` in `keto.yml`, a
directory. It compiles every `*.cue` file there as one CUE package, which is
how one keto-cue serves several services:

- Each file has the clause `package keto`. Two package names in one directory
  are an error.
- Each service declares namespaces only under its own prefix (`chit/`,
  `halo/`). CUE unifies a namespace that two files declare. It does not refuse
  it, so a shared name merges two services' rules.
- Definitions and hidden fields are package-wide: prefix them too
  (`#chit_...`).
- A file may name another service's namespace as a subject type, as
  `internal/keto/testdata/halo.cue` names `chit/actor`.

keto-cue refuses a write to a namespace the schema does not declare (`404`).
It also refuses a check of a relation it does not declare (`400`). So add a
relation to `deploy/keto/schema/chit.cue` before Chit uses it. `make keto-validate`
compiles the directory as the server does, then Chit's file next to the
sample HALO file. `TestKetoSchemaInSync` keeps the ConfigMap copies the same.
`TestKetoSchemaSharesThePackage` checks the package and the prefix. `TestKetoSchemaDeclaresWhatChitUses` checks the
schema against the constants in `internal/model`. Keto runs in its default,
non-strict mode, so checks expand every subject set, as Keto v0.12 did.

### Permission Checks

Keto authorizes slash commands and nothing else. The `chit/command`
namespace uses the `execute` relation. Roles defined in CUE under `auth/` grant
it, and the `chit-reconcile` binary pushes those roles into Keto. The caller
must also be a member of the channel where the caller runs the command.

Channel access checks (read, post, pin, invite) use the PostgreSQL
`channel_members` table and nothing else. chitd never queries the
`chit/channel` namespace.

### Relationship Management

Keto stores a row for every write, even of a tuple it already holds. So the
client lists the exact tuple first and writes only when it is absent.

chitd mirrors channel membership into `chit/channel` on a best-effort basis: a
failed Keto write does not fail the request, and chitd does not retry it.

- **Join channel:** Create `chit/channel:{channel_id}#member@{user_id}`
- **Leave channel, or leave the team that owns it:** Delete
  `chit/channel:{channel_id}#member@{user_id}`

Some members join when a user creates a channel. They are the creator, every
team member of a new open channel, and the participants of a DM or group channel.
chitd writes their tuples in the background, after the response. So the
tuples can appear a moment later.

## Config File References

The Podman Kube manifest holds the Ory configuration files as ConfigMaps:

| File | ConfigMap | Description |
|---|---|---|
| Kratos config | `chit-kratos-config` | Server settings, self-service flows, identity schema |
| Hydra config | `chit-hydra-config` | Ports, issuer URL, opaque 1-hour access tokens, system secret |
| Oathkeeper config | `chit-oathkeeper-config` | Access rules, authenticators, authorizers, mutators |
| Keto config | `chit-keto-config` | Server settings and the CUE permission schema |

The pod spec gives each service its database DSN in the `DSN` environment
variable. The Hydra system secret in the manifest is a
placeholder; change it for anything but local development.

See `deploy/chit.kube.yml` for the full configuration, and the `deploy/`
directory for standalone reference copies.
