---
title: Pub/Sub
description: Cross-node event coordination with PG LISTEN/NOTIFY and NATS.
---

Chit uses a pub/sub abstraction to distribute events beyond the chitd
process. chitd publishes a thin event envelope on the `chit_events` topic
for each broadcast event. Its intended consumer is future multi-node
WebSocket fan-out; `chit-mcp` consumed it historically but now receives
events over chitd's public WebSocket instead (richer payloads, server-side
membership filtering).

:::note[Single-node WebSocket fan-out]
chitd does **not** yet consume the `chit_events` topic itself, so WebSocket
delivery is in-process (single-node). Multi-node fan-out — where a post
created on node A reaches clients connected to nodes B and C — is a planned
use of this same abstraction but is not yet implemented.
:::

## Interface

The pub/sub system is defined as a Go interface, allowing backend
implementations to be swapped without changing application code:

```go
type PubSub interface {
    Publish(channel string, msg []byte) error
    Subscribe(channel string) (<-chan []byte, error)
    Unsubscribe(channel string) error
    Close() error
}
```

## Backends

### PG LISTEN/NOTIFY (Default)

The default backend uses PostgreSQL's built-in `LISTEN/NOTIFY` mechanism.
No additional infrastructure is required — the existing database connection
handles event delivery.

- **Pros:** Zero additional dependencies, transactional consistency
- **Cons:** Limited to ~8KB payload per notification, single PostgreSQL
  instance is the bottleneck

### NATS (Optional)

For higher throughput or larger payloads, Chit supports NATS as an alternative
backend.

- **Pros:** Higher throughput, larger message sizes, clustering support
- **Cons:** Additional infrastructure to deploy and manage

## Backend Selection

Set the `CHIT_PUBSUB_BACKEND` environment variable:

| Value | Backend |
|---|---|
| `pgnotify` | PG LISTEN/NOTIFY (default) |
| `nats` | NATS |

When using NATS, also set `CHIT_NATS_URL`:

```bash
CHIT_PUBSUB_BACKEND=nats
CHIT_NATS_URL=nats://localhost:4222
```

## The `chit_events` Topic

All events are published on a single topic, `chit_events`. Because PostgreSQL
`NOTIFY` payloads are limited to roughly 8KB, the envelopes are deliberately
**thin** — they carry event type, IDs (post, channel, user, and similar), and
timestamps rather than full message content. Consumers fetch full objects
through the REST API using those IDs.

| Producer | Consumer | Purpose |
|---|---|---|
| chitd | chitd (planned) | Multi-node WebSocket fan-out — not yet implemented |

The MCP agent event feed formerly consumed this topic; `chit-mcp` now
listens on chitd's WebSocket (full event payloads, filtered server-side by
the hub) and buffers events for the `get_new_events` MCP tool.
