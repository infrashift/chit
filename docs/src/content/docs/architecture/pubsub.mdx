---
title: Pub/Sub
description: Cross-node event coordination with PG LISTEN/NOTIFY and NATS.
---

Chit uses a pub/sub abstraction to distribute events beyond the chitd
process. chitd publishes a thin event envelope on the `chit_events` topic for
most events it broadcasts. **Nothing in this repository subscribes to that
topic.** `chit-mcp`, `chit-claude` and `chit-tui` receive events over chitd's
WebSocket instead, which carries full payloads and is filtered by membership
in the hub.

:::note[Single-node WebSocket fan-out]
chitd does **not** consume the `chit_events` topic itself, so WebSocket
delivery is in-process (single-node). Multi-node fan-out, where a post
created on node A reaches clients connected to nodes B and C, is a planned
use of this abstraction but is not implemented.
:::

## Interface

The pub/sub system is a Go interface (`internal/pubsub/pubsub.go`), so the
backend can be swapped without changing application code:

```go
type PubSub interface {
    Publish(ctx context.Context, topic string, data []byte) error
    Subscribe(ctx context.Context, topic string, handler func(data []byte)) error
    Close() error
}
```

`Subscribe` registers a callback that is invoked for each message on the
topic. There is no `Unsubscribe`; subscriptions end when the backend is
closed.

## Backends

### PG LISTEN/NOTIFY (Default)

The default backend uses PostgreSQL's built-in `LISTEN/NOTIFY` (`pg_notify`).
No additional infrastructure is required; it uses the existing database pool.
Topic names must be valid PostgreSQL identifiers
(`^[a-zA-Z_][a-zA-Z0-9_]{0,62}$`). The listener reconnects and re-`LISTEN`s
after a connection failure.

- **Pros:** Zero additional dependencies
- **Cons:** Payloads limited to about 8KB per notification; the single
  PostgreSQL instance is the bottleneck

### NATS (Optional)

For higher throughput or larger payloads, Chit supports NATS as an alternative
backend.

- **Pros:** Higher throughput, larger message sizes, clustering support
- **Cons:** Additional infrastructure to deploy and manage

## Backend Selection

Set the `CHIT_PUBSUB_BACKEND` environment variable:

| Value | Backend |
|---|---|
| `pgnotify` | PG LISTEN/NOTIFY (default) |
| `nats` | NATS |

Any other value is refused at startup. When using NATS, `CHIT_NATS_URL` is
required:

```bash
CHIT_PUBSUB_BACKEND=nats
CHIT_NATS_URL=nats://localhost:4222
```

## The `chit_events` Topic

Events are published on a single topic, `chit_events`. Because PostgreSQL
`NOTIFY` payloads are limited to roughly 8KB, the envelopes
(`internal/pubsub/events.go`) are deliberately **thin**: an event type and
identifiers, with no content and no timestamp.

```json
{
  "event": "mentioned",
  "post_id": "01912345-...",
  "channel_id": "01912345-...",
  "team_id": "",
  "target_user_id": "01912345-..."
}
```

| Field | Set for |
|---|---|
| `event` | Always: the WebSocket event name |
| `post_id` | Post events and `mentioned` |
| `channel_id` | Every published event |
| `team_id` | `channel_created`, `channel_updated` (empty for DMs and groups) |
| `target_user_id` | `mentioned` only: the mentioned user |

Empty fields are omitted. Envelopes are published for `posted`,
`post_edited`, `post_deleted`, `post_pinned`, `post_unpinned`,
`channel_created`, `channel_updated`, `channel_deleted`, `user_added`,
`user_removed` and `mentioned`. `typing`, `thread_updated` and
`command_response` go to the WebSocket hub only.

A publish failure is logged at Warn and does not fail the request.

| Producer | Consumer | Purpose |
|---|---|---|
| chitd | none | Reserved for multi-node WebSocket fan-out, which is not implemented |
