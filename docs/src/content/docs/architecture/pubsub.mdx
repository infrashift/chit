title: Pub/Sub
description: Cross-node event coordination with PG LISTEN/NOTIFY and NATS.

Chit uses a pub/sub interface to send events outside the chitd process.
chitd publishes a thin event envelope on the `chit_events` topic for most
events it broadcasts. **Nothing in this repository subscribes to that
topic.** `chit-mcp`, `chit-claude` and `chit-tui` receive events over chitd's
WebSocket instead. The WebSocket carries full payloads, and the hub filters
them by membership.

:::note[Single-node WebSocket fan-out]
chitd does **not** consume the `chit_events` topic itself, so WebSocket
delivery is in-process (single-node). Multi-node fan-out is a planned use of
this interface, but it is not implemented. With it, a post created on node A
reaches clients connected to nodes B and C.
:::

## Interface

The pub/sub system is a Go interface (`internal/pubsub/pubsub.go`). So an
operator can replace the backend, and the application code stays the same:

```go
type PubSub interface {
    Publish(ctx context.Context, topic string, data []byte) error
    Subscribe(ctx context.Context, topic string, handler Handler) error
    Close() error
}

// Handler receives the messages published on a subscribed topic.
type Handler interface {
    Handle(data []byte)
}
```

`Subscribe` registers a handler. The backend calls its `Handle` method for
each message on the topic. There is no `Unsubscribe`; subscriptions end when
the backend closes.

## Backends

### PG LISTEN/NOTIFY (Default)

The default backend uses PostgreSQL's built-in `LISTEN/NOTIFY` (`pg_notify`).
It needs no additional infrastructure; it uses the database pool of chitd.
Topic names must be valid PostgreSQL identifiers
(`^[a-zA-Z_][a-zA-Z0-9_]{0,62}$`). The listener reconnects and re-`LISTEN`s
after a connection failure.

- **Pros:** Zero additional dependencies
- **Cons:** Payloads limited to about 8KB per notification; the single
  PostgreSQL instance is the bottleneck

### NATS (Optional)

For higher throughput or larger payloads, Chit supports NATS as an alternative
backend.

- **Pros:** Higher throughput, larger message sizes, NATS clusters
- **Cons:** Additional infrastructure to deploy and manage

## Backend Selection

Set the `CHIT_PUBSUB_BACKEND` environment variable:

| Value | Backend |
|---|---|
| `pgnotify` | PG LISTEN/NOTIFY (default) |
| `nats` | NATS |

chitd refuses all other values at startup. With NATS, `CHIT_NATS_URL` is
mandatory:

```bash
CHIT_PUBSUB_BACKEND=nats
CHIT_NATS_URL=nats://localhost:4222
```

## The `chit_events` Topic

chitd publishes events on a single topic, `chit_events`. The maximum
PostgreSQL `NOTIFY` payload is about 8KB. So the envelopes
(`internal/pubsub/events.go`) are deliberately **thin**: an event type and
identifiers, with no content and no timestamp.

```json
{
  "event": "mentioned",
  "post_id": "01912345-...",
  "channel_id": "01912345-...",
  "team_id": "",
  "target_user_id": "01912345-..."
}
```

| Field | Set for |
|---|---|
| `event` | Always: the WebSocket event name |
| `post_id` | Post events and `mentioned` |
| `channel_id` | Every published event |
| `team_id` | `channel_created`, `channel_updated` (empty for DMs and groups) |
| `target_user_id` | `mentioned` only: the mentioned user |

An envelope omits empty fields. chitd publishes envelopes for `posted`,
`post_edited`, `post_deleted`, `post_pinned`, `post_unpinned`,
`channel_created`, `channel_updated`, `channel_deleted`, `user_added`,
`user_removed` and `mentioned`. For a channel tag, chitd also publishes
envelopes for `post_tags_updated`, `channel_tags_updated`, `tag_updated` and
`tag_deleted`. A change to a private tag gives no envelope. `typing`,
`thread_updated`, `command_response` and `stream_status` go to the WebSocket
hub only.

chitd logs a publish failure at Warn, and the request does not fail.

| Producer | Consumer | Purpose |
|---|---|---|
| chitd | none | Reserved for multi-node WebSocket fan-out, which is not implemented |
