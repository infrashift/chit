[`api/openapi.yaml`](https://github.com/infrashift/chit/blob/main/api/openapi.yaml)
defines the Chit REST API as an OpenAPI 3.1 document. chitd serves the same
spec at `GET /api/v1/openapi.yaml` and a Swagger UI at `/api/v1/docs/`.

## Base URL

```
/api/v1
```

## Authentication

These endpoints need no authentication: `/system/ping`,
`/system/config/client`, `/openapi.yaml`, and `/docs/`. Every other endpoint
requires one of two headers, which only the auth proxy (Ory Oathkeeper) may
set:

| Header | Caller | Resolution |
|---|---|---|
| `X-Client-Id` | A machine actor holding a Hydra `client_credentials` token | Matched against `users.oauth_client_id`. An unknown client is a `401`; there is no automatic provisioning. Takes precedence over `X-User-Id`. |
| `X-User-Id` | A person with a Kratos session | The Kratos identity ID. On first sight chitd provisions a local user from the identity's Kratos traits. Without a `username` trait the username is derived: the email's local part reduced to `a-z 0-9 . _ -`, then `-` and the first 8 hex digits of the Kratos ID (`user-` and 12 digits without an email); a taken name gets a longer suffix. |

chitd validates no session or token itself; it trusts these headers. When
the operator sets `CHIT_TRUSTED_PROXY_SECRET`, every authenticated request must
also have an `X-Proxy-Secret` header with the same value. Else chitd refuses
it with `401`. The operator can change the header names
(`CHIT_TRUSTED_PROXY_HEADER`, `CHIT_TRUSTED_CLIENT_HEADER`).

See [Ory Stack](/chit/deployment/ory-stack/) for the full authentication flow.

### On behalf of a person

A machine actor whose OAuth2 client is in `CHIT_ON_BEHALF_OF_CLIENTS` may act
as a person. To do this, it names the person in `X-On-Behalf-Of`. chitd then
authorizes the request as the person, with all the checks that apply to the
person. The audit log records the client beside the person. The value is one
of:

- the person's Chit user ID;
- `kratos:` and the person's Kratos identity ID, as a canonical (lowercase,
  hyphenated) UUID. If the identity has no Chit user yet, chitd provisions one
  from the Kratos traits. It does exactly what it does on the first browser
  request of the person. It also writes a `user_provisioned` audit record.

chitd accepts the header only on these routes. On all other routes, the header
gives a `400`:

| Method | Path | As the person |
|---|---|---|
| POST | `/posts` | Post; `props.on_behalf_of.actor_id` names the client |
| POST | `/channels/{id}/stream_status` | Send a stream status |
| POST | `/tags`, `/posts/{id}/tags`, `/channels/{id}/tags` | Create and apply tags |
| GET | `/tags`, `/channels/{id}/tags` | List the person's tags: their private tags and the channel tags of their channels, never another person's private tag |
| POST | `/tags/posts`, `/tags/channels` | Read tags of many posts, and filter the person's channels by tags |
| DELETE | `/posts/{id}/tags/{tag_id}`, `/channels/{id}/tags/{tag_id}` | Remove a tag; another person's private tag is a `404` |
| POST | `/channels/{id}/files` | Upload an image; the person is `uploader_id`, the client `via_actor_id`, and a `file_uploaded` audit record names both |
| GET | `/files/{id}` | Download an image the person may read (halod proxies downloads) |
| POST | `/channels` | Create a channel; the person must be on the team, and is its creator |
| POST | `/channels/{id}/members` | Add a member; the person must be allowed to add one |
| GET | `/users/me` | Return the person: how a client learns a `kratos:` person's user ID |

A request on behalf of a person counts against the person's per-user rate
limit and the client's aggregate one; what the client does as itself counts
against its aggregate limit only (see
[Rate limits](/chit/reference/configuration/#rate-limits)).

Refused: a client not on the list, or a person's session, with the header
(`403`); an empty or malformed value, an unknown user or Kratos identity, a
deactivated person (in Chit, or inactive in Kratos), and an agent or bot
(`400`). A machine actor learns its own user ID with `GET /users/me` and no
`X-On-Behalf-Of`.

HALO creates a Conversation with these requests:

1. `GET /users/me` for the person (`kratos:<id>`).
2. `POST /teams/{id}/members` as halod, to add the person to halod's team.
3. `POST /channels` with `"type": "P"` for the person.
4. `POST /channels/{id}/members` with halod's user ID, for the person.
5. `POST /posts` for the person.
6. `GET /channels/{id}/posts` as halod, which is now a member.

### Membership hook

When `CHIT_MEMBERSHIP_HOOK_URL` is set, chitd asks the hook before it adds a
member to a channel: `POST /channels/{id}/members` (a join and an
on-behalf-of add included), the team members of a new Open channel, the
other members of a new direct or group channel, and `/invite`. The creator of
a new channel is not asked about. Any answer but `{"allow": true}` refuses
the add, a failed or slow hook included. A refused request adds nobody,
however many members it adds, and answers `403`:

```json
{"id": "channel.membership_refused", "status_code": 403,
 "message": "the membership policy refused to add user <user ID> to this channel",
 "reason": "<the hook's code, or hook_unavailable>",
 "detail": "<the hook's text for a person>"}
```

[Configuration](/chit/reference/configuration/#membership-hook) gives the
hook's request and answer.

## Limits

| Limit | Value | Response |
|---|---|---|
| Rate limit, per user | `CHIT_RATE_LIMIT_USER_PER_SECOND` (10) requests/s, burst `CHIT_RATE_LIMIT_USER_BURST` (50); on behalf of a person, the person's | `429`, `Retry-After` |
| Rate limit, per on-behalf-of client | `CHIT_RATE_LIMIT_CLIENT_PER_SECOND` (1500) requests/s, burst `CHIT_RATE_LIMIT_CLIENT_BURST` (3000), for all it does | `429`, `Retry-After` |
| Request body | 1 MiB | `413` |
| Malformed JSON body | | `400` |
| Post content | 65,535 bytes | `400` |
| `POST /users/ids`, `POST /tags/posts` | 200 IDs per request | `400` |
| Upload (`POST /channels/{id}/files`) | 10 MiB, before and after re-encoding | `413` |
| Image size | 40,000,000 pixels, from the header | `422` |
| Attachments per post | 4 | `400` |
| Stored attachments per person | `CHIT_FILE_QUOTA_BYTES` (1 GiB) | `413` |

By default, chitd validates each request against the OpenAPI spec
(`CHIT_ENABLE_OPENAPI_VALIDATION`). chitd refuses a request that the spec does
not allow before the request reaches a handler.

## Pagination

List endpoints accept query parameters:

| Parameter | Type | Default | Description |
|---|---|---|---|
| `page` | int | `0` | Page number (0-indexed) |
| `per_page` | int | `60` (`25` for the thread inbox) | Results per page |

The server clamps the values. `page` is at least `0`, and `per_page` is
between 1 and 200. The server also decreases `page` until `page * per_page` is
not more than 100,000. Search takes the same two fields in its JSON body, and
the server clamps them the same way.

List endpoints return `[]`, never `null`, when there is nothing to list.

## ID Format

All resource IDs are **UUIDv7** strings (e.g., `01912345-6789-7abc-8def-0123456789ab`).
A UUIDv7 starts with a timestamp, so the IDs sort in time order.

## Timestamps

All `*_at` fields are **Unix millisecond timestamps** (int64).

## Endpoints

### System and documentation

| Method | Path | Summary |
|---|---|---|
| GET | `/system/ping` | Health check (`{"status":"OK"}`) |
| GET | `/system/config/client` | Client configuration (`{"version": ...}`) |
| GET | `/openapi.yaml` | The OpenAPI spec |
| GET | `/docs/` | Swagger UI |

### Users

| Method | Path | Summary | Who may call |
|---|---|---|---|
| POST | `/users` | Create a user, including a machine actor bound to an OAuth2 client | `system_admin` |
| GET | `/users?term=` | Search users by username or display name (substring; `%` and `_` are literal) | Any user |
| GET | `/users/me` | Get the caller; with `X-On-Behalf-Of`, the person (provisioned for `kratos:`) | Any user |
| PUT | `/users/me` | Change the caller's `username` and/or `display_name`; a taken username is `409` | Any user |
| GET | `/users/{id}` | Get user by ID | Any user |
| GET | `/users/username/{username}` | Get user by username | Any user |
| POST | `/users/ids` | Get users by IDs (JSON array of IDs) | Any user |

Users returned by the lookup and search endpoints have `email`, `kratos_id`
and `oauth_client_id` removed. Only `GET /users/me` (and the `POST /users`
response) include them.

### Teams

| Method | Path | Summary | Who may call |
|---|---|---|---|
| POST | `/teams` | Create a team; the creator becomes `team_admin` | Any user |
| GET | `/teams` | List open teams plus the caller's teams (all teams for `system_admin`) | Any user |
| GET | `/teams/{id}` | Get a team | Anyone for open teams; members or `system_admin` for invite-only |
| PUT | `/teams/{id}` | Update `display_name`, `description`, `type`. `name` cannot change (`400`). | `team_admin` of the team, or `system_admin` |
| DELETE | `/teams/{id}` | Soft-delete the team and all its channels | `team_admin` of the team, or `system_admin` |
| GET | `/users/me/teams` | The caller's teams | Any user |
| POST | `/teams/{id}/members` | Add a user (`{"user_id": ...}`) | Anyone, to join an open team themselves; otherwise team members |
| GET | `/teams/{id}/members` | List members | Team members or `system_admin` |
| DELETE | `/teams/{id}/members/{user_id}` | Remove a member, and remove them from every channel on the team | The member themselves; `system_admin` for anyone else |

### Channels

| Method | Path | Summary | Who may call |
|---|---|---|---|
| POST | `/channels` | Create an open (`O`) or private (`P`) channel. `team_id` is required. For an open channel every team member is added. | Team members |
| GET | `/channels/{id}` | Get a channel | Members; also team members for an open channel |
| PUT | `/channels/{id}` | Update `display_name`, `header`, `purpose`. `name` cannot change (`400`). | Channel members |
| DELETE | `/channels/{id}` | Soft-delete a channel | Its creator, or `system_admin` |
| GET | `/teams/{id}/channels` | The team's **open** channels, to browse and join | Team members |
| GET | `/users/me/teams/{id}/channels` | The caller's channels in a team, private ones included | Any user (own channels only) |
| GET | `/users/me/channels/direct` | The caller's direct and group channels | Any user |
| POST | `/channels/direct` | Open the DM between two users (JSON array of exactly 2 IDs); returns the existing one if there is one | One of the two users |
| POST | `/channels/group` | Open a group channel (JSON array of 3 to 8 distinct IDs); returns the existing one if there is one | One of the members |
| POST | `/channels/{id}/members` | Add a user (`{"user_id": ...}`) who must be on the channel's team. Re-adding is a no-op. | Open: team members. Private: channel members. Direct and group: nobody (`403`) |
| GET | `/channels/{id}/members` | List members | Channel members |
| DELETE | `/channels/{id}/members/{user_id}` | Remove a member | The member themselves; `system_admin` for anyone else |
| POST | `/channels/{id}/members/me/view` | Mark the channel read | Channel members |

Only `/channels/direct` and `/channels/group` can create direct and group
channels. Their membership cannot change.

### Posts

| Method | Path | Summary | Who may call |
|---|---|---|---|
| POST | `/posts` | Create a post or reply (`channel_id`, `content`, optional `root_id`, `props`, `file_ids`). Slash commands are intercepted here. | Channel members |
| GET | `/posts/{id}` | Get a post | Channel members |
| PUT | `/posts/{id}` | Edit `content` and/or merge `props` (a `null` value deletes a key); returns the whole post | The author, or `system_admin` |
| DELETE | `/posts/{id}` | Soft-delete a post | The author, or `system_admin` |
| POST | `/posts/{id}/pin` | Pin a post | Channel members |
| POST | `/posts/{id}/unpin` | Unpin a post | Channel members |
| GET | `/channels/{id}/posts` | Posts in a channel, newest first | Channel members |
| GET | `/channels/{id}/pinned` | Pinned posts in a channel | Channel members |

A reply's `root_id` must name a root post (not a reply) in the same channel.
Else the request gets a `400`. The server computes `props.mentions` from the
content, and ignores a value from the client.

`GET /channels/{id}/posts` also accepts a `since` query parameter (Unix
milliseconds). With `since`, it returns the posts created after that time,
oldest first. A client uses it to poll for new posts.

`file_ids` attaches up to 4 files the author uploaded to the same channel
and has not attached elsewhere (otherwise `400`; `409` if one was attached
meanwhile). A post with files needs no `content`, and is never run as a slash
command. Posts read back with `file_ids` in order. Deleting a post deletes its
files.

A slash command (content matching `^/[a-z0-9-]+`) is executed rather than
stored; the response is a stand-in post that is not persisted. See
[MCP and Slash Commands](/chit/reference/mcp-and-commands/#slash-commands).

### Threads

| Method | Path | Summary | Who may call |
|---|---|---|---|
| GET | `/posts/{id}/thread` | A root post and all its replies | Channel members |
| GET | `/users/me/teams/{id}/threads` | The caller's thread inbox for a team: followed threads in channels they still belong to, newest reply first, each with its root post, `last_viewed_at` and `unread_mentions` | Any user (own inbox only) |
| PUT | `/users/me/teams/{team_id}/threads/{id}/read` | Mark a thread read | Members of the root's channel |
| PUT | `/users/me/teams/{team_id}/threads/{id}/following` | Follow or unfollow (`{"following": bool}`) | Members of the root's channel |
| GET | `/users/me/threads/direct` | The caller's thread inbox for direct and group channels, which belong to no team and so never appear in a team's inbox. Same shape and filtering as the team inbox | Any user (own inbox only) |
| PUT | `/users/me/threads/{id}/read` | As the team-scoped route, without a `team_id` (which that route ignores); use it for DM and group threads | Members of the root's channel |
| PUT | `/users/me/threads/{id}/following` | As the team-scoped route, without a `team_id` | Members of the root's channel |

A user who replies to a thread follows it. At the first reply, the root's
author also follows the thread, unless the author already has a membership
(for example, the author unfollowed).

### Tags

| Method | Path | Summary | Who may call |
|---|---|---|---|
| POST | `/tags` | Create a tag owned by the caller: `{"name", "scope": "private" (default) or "channel", "channel_id"}`. Idempotent per scope. | Any user; a member of `channel_id` for a channel tag |
| GET | `/tags` | The tags the caller can see (`?channel_id=` narrows to one channel) | Any user |
| PUT | `/tags/{id}` | Rename (`{"name"}`) | The owner |
| DELETE | `/tags/{id}` | Delete, with every application | The owner |
| POST | `/posts/{id}/tags` | Tag a post (`{"tag_id": ...}`) | Members of the post's channel; a private tag by its owner only |
| GET | `/posts/{id}/tags` | The tags on a post the caller can see | Members of the post's channel |
| DELETE | `/posts/{id}/tags/{tag_id}` | Remove a tag from a post | Members for a channel tag; the owner for a private tag |
| POST | `/tags/posts` | Visible tags for many posts (`{"post_ids": [...]}`, at most 200), keyed by post ID. Posts the caller cannot read are omitted. | Any user |
| POST | `/channels/{id}/tags` | Tag a channel (`{"tag_id": ...}`) | Members; a private tag by its owner only |
| GET | `/channels/{id}/tags` | The tags on a channel the caller can see | Members |
| DELETE | `/channels/{id}/tags/{tag_id}` | Remove a tag from a channel | Members for a channel tag; the owner for a private tag |
| POST | `/tags/channels` | The caller's channels that have **all** of up to 8 tags (`{"tag_ids", "team_id"}`), on the channel or one of its posts, each with its visible channel tags | Any user |
| DELETE | `/users/{id}/tags` | Delete every tag the user owns (for deleting or anonymizing a person) | The user or a system_admin |

**Scopes.** A `private` tag is its owner's alone. Nobody else sees it, its
name, or what it is on, in a list, read, search, filter or WebSocket event. A
request with its ID gets 404, as for an unknown tag. A `channel` tag belongs
to one channel. Every member sees it and may apply or remove it in that
channel, and only there. Only the owner renames or deletes a tag. A name has 1
to 50 characters (letters, digits, space, `-`, `_`, `.`). It is unique per
owner (private) or per channel (channel). To compare names, chitd applies NFKC
and a simple change to lowercase (so `ß` and `ss` are different names).
An item has at most 32 channel tags and 32 private tags of each owner; an
owner owns at most 1024 tags. Each application records `applied_by`.

**Only HALO uses `profile/`**, for its Profile tags. A person cannot create,
rename or apply such a tag (403). An OAuth2 client in
`CHIT_ON_BEHALF_OF_CLIENTS` may create one and apply it with
`X-On-Behalf-Of`, only as the person's private tag.

### Files

Image attachments (HALO P-CHIT-5). Off unless `CHIT_S3_ENDPOINT` is set: then
every file route, and `file_ids` on a post, answer `503`.

| Method | Path | Summary | Who may call |
|---|---|---|---|
| POST | `/channels/{id}/files` | Upload one image (multipart: `file`, optional `alt_text`); returns the `File` (`201`) | Channel members |
| GET | `/files/{id}` | The image's bytes | Channel members once it is attached; before, its uploader only |
| GET | `/files/{id}/info` | The `File` | As `GET /files/{id}` |
| POST | `/files/search` | Files whose name or alt text contains `terms` (`{"terms", "channel_id", "page", "per_page"}`), newest first | Any user, over their channels |

**Validation.** The `file` part's `Content-Type` is the declared type and its
filename the name. Chit accepts only `image/png`, `image/jpeg`, `image/webp`
and `image/gif` (the first frame only); refuses SVG; refuses a declared type
that is not the type of the magic bytes, and a polyglot (bytes after the end
of the image, or markup in its metadata); reads the size with
`image.DecodeConfig` and refuses more than 40,000,000 pixels before decoding;
then decodes and re-encodes the image in pure Go, JPEG as JPEG and the others
as PNG, so no EXIF, text chunk or trailing byte is stored. The rules are in
the package `github.com/infrashift/chit/pkg/imagecheck`, which has no Chit
dependencies, so HALO applies the same ones to generated images.

| Refusal | Status | `id` |
|---|---|---|
| Over 10 MiB, before or after re-encoding | `413` | `file.too_large` |
| The person's stored files would pass `CHIT_FILE_QUOTA_BYTES` | `413` | `file.quota_exceeded` |
| SVG, by type or by content | `415` | `file.svg` |
| Not one of the four types | `415` | `file.unsupported_type` |
| Declared and sniffed types differ | `415` | `file.type_mismatch` |
| Trailing bytes, or markup in metadata | `422` | `file.polyglot` |
| More than 40,000,000 pixels | `422` | `file.too_many_pixels` |
| Does not decode | `422` | `file.malformed` |

**Storage.** The bytes are stored in the S3 bucket `CHIT_S3_BUCKET`
(`chit-files`) under `<channel_id>/<file_id>`. An upload with the bytes of a
live file in the same channel gets its own file (its own ID, uploader and alt
text) that shares that object; another channel never shares it. An upload
attached to no post after `CHIT_FILE_ORPHAN_GRACE` (24 h) is deleted, and a
deleted file's object is removed that long after, unless a live file still
uses it, by a sweep of at most `CHIT_FILE_SWEEP_BATCH` files every
`CHIT_FILE_SWEEP_INTERVAL`.

**Headers.** Every response of these routes, refusals included, carries
`X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` and
`Content-Disposition: attachment` (with the file name on a download). A
download also has `Cache-Control: private, no-store` and the SHA-256 as its
`ETag`. There are no public or presigned URLs.

**Search** matches the file name and the alt text the person wrote, never the
image or anything derived from it. A file not yet attached is found only by
its uploader.

### Search

| Method | Path | Searches |
|---|---|---|
| POST | `/posts/search` | Every channel the caller belongs to |
| POST | `/teams/{id}/posts/search` | The caller's channels in team `{id}`; requires team membership (`403`) |
| POST | `/channels/{id}/posts/search` | Channel `{id}`; requires channel membership (`403`) |

Request body:

| Field | Type | Description |
|---|---|---|
| `terms` | string | Text to find. Optional if `tag_ids` is given. |
| `tag_ids` | string[] | Up to 8 tag UUIDs; a post must carry **all** of them. Only tags the caller can see filter: another user's private tag, like an unknown tag, matches nothing. Optional if `terms` is given. |
| `from` | string | Author username; a leading `@` is accepted. An unknown author matches nothing. |
| `page` | int | Page number, default `0` |
| `per_page` | int | Page size, default `60` |

The body must have `terms`, `tag_ids` or both (else `400`). The response is
`{"order": [posts]}`. chitd applies scope, author and tags before it cuts the
page. So a page is short only at the end of the results.

With `CHIT_ZINCSEARCH_URL` unset (the default), search runs in PostgreSQL. It
does a case-insensitive match on a part of the content (`%` and `_` are
literal), newest first. With `CHIT_ZINCSEARCH_URL` set, term searches go to
ZincSearch, best match first. chitd filters the hits to the caller's scope
and reads at most 1,000 hits per search. If ZincSearch fails, the search falls back to SQL.

## Responses

Endpoints with nothing to return answer `200` with `{"status":"OK"}`.
Endpoints that create a resource answer `201` with the new resource.

## Error Format

All error responses use the same JSON shape (`model.AppError`):

```json
{
  "id": "App.requireChannelMember",
  "message": "not a member of this channel",
  "status_code": 403
}
```

| Field | Description |
|---|---|
| `id` | Where the error was raised (e.g. `App.requireChannelMember`) |
| `message` | Human-readable description |
| `detailed_error` | Extra detail for a 4xx, when there is any. Omitted when empty, and **never sent with a 5xx**: a server error's cause is logged, not returned. |
| `status_code` | The HTTP status, repeated |

Authorization failures are `403`. An absent or unknown resource is `404`.
A conflict (such as a taken username) is `409`.
