title: WebSocket Protocol
description: Wire format, event types, client actions, and connection lifecycle.

Chit provides real-time event delivery over WebSocket connections.

## Connection Endpoint

```
GET /api/v1/websocket
```

Upgrade a standard HTTP connection to WebSocket. The endpoint has the same
authentication as the REST API. The request must come through Oathkeeper with
the trusted `X-User-Id` (Kratos session) or `X-Client-Id` (OAuth2 client
credentials) header. An unauthenticated request gets the API's JSON `401`
error instead of an upgrade.

chitd checks the browser `Origin` header against `CHIT_ALLOWED_ORIGINS`. chitd
accepts a request with no `Origin` (a non-browser client such as `chit-tui` or
`chit-mcp`). `*` accepts any origin. An empty value accepts no browser origin.
A refused origin fails the upgrade.

## Wire Format

### Server → Client Events

Every event has the same envelope:

```json
{
  "event": "post_deleted",
  "data": {
    "post_id": "01912345-...",
    "channel_id": "01912345-..."
  },
  "broadcast": {
    "channel_id": "01912345-..."
  },
  "seq": 0
}
```

| Field | Type | Description |
|---|---|---|
| `event` | string | Event type identifier |
| `data` | object | Event payload (varies by event type, see below) |
| `broadcast` | object | Who the event was addressed to: `channel_id`, `team_id` or `user_id`. Empty fields are omitted. |
| `seq` | int64 | Always `0` from chitd. chitd does not number events; only `chit-mcp`'s event buffer assigns sequence numbers, for its `get_new_events` tool. |

### Client → Server Messages

```json
{
  "action": "typing",
  "data": {
    "channel_id": "01912345-..."
  }
}
```

| Field | Type | Description |
|---|---|---|
| `action` | string | Action identifier. Only `typing` is accepted; anything else is ignored. |
| `seq` | int64 | Accepted for compatibility and ignored |
| `data` | object | Action payload |

chitd logs and ignores a message that is not valid JSON. A message larger than
**4096 bytes** closes the connection.

## Server → Client Event Types

chitd sends 19 event types.

| Event | `data` | `broadcast` | Sent when |
|---|---|---|---|
| `posted` | The full post object (`id`, `channel_id`, `user_id`, `root_id`, `content`, `type`, `props`, `is_pinned`, `create_at`, …) | `channel_id` | A post or reply is created |
| `post_edited` | The full post object, as stored after the edit | `channel_id` | A post is edited |
| `post_deleted` | `post_id`, `channel_id` | `channel_id` | A post is deleted |
| `post_pinned` | `post_id`, `channel_id` | `channel_id` | A post is pinned |
| `post_unpinned` | `post_id`, `channel_id` | `channel_id` | A post is unpinned |
| `typing` | `user_id` | `channel_id` | A member sends the `typing` action |
| `channel_created` | The full channel object | `team_id` for an open channel; `channel_id` for private, direct and group channels | A channel, DM or group channel is created |
| `channel_updated` | The full channel object | As for `channel_created` | A channel's display name, header or purpose changes (including via `/topic`) |
| `channel_deleted` | `channel_id` | `channel_id` | A channel is deleted, or its team is deleted |
| `user_added` | `channel_id`, `user_id` (the user added) | `channel_id` | A user joins or is added through `POST /channels/{id}/members` or `/invite`. Members added when a channel is created are announced by `channel_created` instead. |
| `user_removed` | `channel_id`, `user_id` (the user removed) | `channel_id`, and separately `user_id` (the user removed) | A user leaves or is removed from a channel, including by leaving or being removed from its team |
| `thread_updated` | `thread`: `{post_id, channel_id, reply_count, last_reply_at, participants}` | `channel_id` | After every reply, and after every reply deletion |
| `post_tags_updated` | `post_id`, `channel_id`, `tags` (the post's tag list **as the recipient sees it**) | `user_id`, one event per recipient: every channel member for a channel tag, the owner alone for a private tag | A tag is added to or removed from a post |
| `channel_tags_updated` | `channel_id`, `tags` (the channel's own tags as the recipient sees them) | `user_id`, as for `post_tags_updated` | A tag is added to or removed from a channel |
| `tag_updated` | `tag` | `channel_id` for a channel tag; `user_id` (the owner) for a private tag | A tag is renamed |
| `tag_deleted` | `tag_id` | As for `tag_updated` | A tag is deleted |
| `mentioned` | `post_id`, `channel_id`, `user_id` (the post's **author**) | `user_id` (the mentioned user) | A post mentions the user, by `@username` or `@all` |
| `command_response` | `text`, `command_slug`, `channel_id` | `user_id` (the invoker) | A slash command handler ran. See [MCP and Slash Commands](/chit/reference/mcp-and-commands/). |
| `stream_status` | `channel_id`, `user_id`, `status` (`started`, `progress`, `finished`), and `stream_id` and `actor_id` when set | `channel_id` | A member, or an allowlisted client on behalf of one, calls `POST /channels/{id}/stream_status` while producing a reply. Never stored; two a second per sender and channel, in bursts of five. |

Notes:

- `posted` and `post_edited` carry the post's fields directly in `data`; there
  is no `post` wrapper.
- `thread_updated` deliberately does not carry the reply. The reply itself
  arrives as `posted`.
- chitd sends `user_removed` two times. One copy goes to the members that
  stay in the channel. The other copy goes to the removed user. When the hub
  delivers the channel copy, the removed user is no longer in the channel's
  audience. Each connection receives the event one time.
- chitd sends a `command_response` only when a handler ran, whatever text it
  returned. An unknown command, a permission denial, a command with no
  handler, or a handler error answers only through the `POST /posts`
  response.
- There is no online-status or `status_change` event.
- chitd relays `stream_status`, like `typing`, and never stores it: no post, no
  counter, no pubsub envelope. HALO's halod sends it while it streams a reply
  to the requester, so the channel's other members see activity.

## Client → Server Actions

| Action | Data Fields | Description |
|---|---|---|
| `typing` | `channel_id` | Notify the channel that the user is typing |

The hub relays a `typing` action only if the sender is a member of
`channel_id` (per the hub's membership cache). The hub delivers it to every
connected member of the channel, also to the sender's own connections.

## Broadcast Targeting

The hub decides who receives each event from its `broadcast` object:

1. **`user_id` set:** delivered only to that user's connections. The hub
   ignores `channel_id` and `team_id`.
2. **Otherwise `channel_id` set:** delivered only to connected members of that
   channel.
3. **Otherwise `team_id` set:** delivered only to connected members of that
   team.
4. **All empty:** delivered to every connected client. chitd does not
   currently send such an event.

The hub drops an event with no `broadcast` object.

Channel and team membership come from a per-user cache. The hub loads it from
the database when the user's first connection registers (with a 10-second
timeout). Until that load finishes, the hub does not deliver channel- and
team-targeted events to that user. If the load fails, the hub tries it again
on the user's next connection. The hub queues membership changes that occur
during the load, and applies them after the load. So the hub does not lose
them. The hub drops the cache when the user's last connection closes.

## Connection Lifecycle

1. **Connect:** the client upgrades at `/api/v1/websocket`.
2. **Register:** the hub registers the connection. Then it starts the read and
   write pumps. The first connection of a user starts the membership load.
3. **Receive events:** the hub writes events to the connection. These are
   the events for the user, the user's channels or the user's teams.
4. **Send actions:** the client may send `typing` actions.
5. **Ping/Pong:** the server sends a ping every `CHIT_WS_PING_INTERVAL`
   (default `30s`). The read deadline is two times that interval. Only a pong
   moves the read deadline forward. So the server disconnects a client that
   does not answer pings. Each write has a deadline of `CHIT_WS_WRITE_TIMEOUT`
   (default `10s`).
6. **Disconnect:** the connection closes for one of these causes. The client
   closes it, a ping times out, a write fails, or the server drops a slow
   consumer (below). The hub then unregisters the connection.

### Slow consumers

Each connection has a send buffer of **256 events**. If an event arrives while
the buffer is full, the hub disconnects that connection. It does not block,
and it does not silently drop events. This has no effect on other connections,
also not on the same user's other connections.

## Reconnection

chitd does not replay events, and a client cannot find gaps with `seq`. A
client can reconnect, or the server can disconnect it as a slow consumer. In
both cases, the client must reconnect with backoff and fetch again what it
shows, for example with `GET /channels/{id}/posts?since=<last create_at>`.
