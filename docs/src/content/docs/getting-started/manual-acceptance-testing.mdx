title: Manual Acceptance Testing
description: Spin up a self-contained UAT environment with pre-seeded users for manual testing.
---

The UAT environment runs the full Ory stack (Kratos, Oathkeeper, Keto) with
chitd and PostgreSQL in a Podman pod. Five test users are pre-seeded with
Kratos identities so you can test both API access and chit-tui login.

## Prerequisites

| Dependency | Version | Purpose |
|---|---|---|
| Podman | 4.0+ | Run the UAT pod |
| Go | 1.24+ | Run the Kratos seed script |

## Start the environment

```bash
make uat-up
```

This builds the container images, creates a Podman pod, starts PostgreSQL,
runs migrations, seeds chit test data, and starts all services (Kratos,
Oathkeeper, Keto, chitd, Zincsearch).

Watch the server logs to confirm all services are ready:

```bash
podman logs -f chit-uat-app-chitd
```

### Seed Kratos identities

After the pod is fully running, create Kratos identities so users can log in:

```bash
make uat-seed-kratos
```

This creates password-based identities in Kratos for all 5 test users.
The script waits for Kratos to be ready before proceeding. It is idempotent
and safe to run multiple times.

## Verify

```bash
# Direct server access
curl http://localhost:8065/api/v1/system/ping

# Through Oathkeeper proxy
curl http://localhost:4455/api/v1/system/ping
```

Expected response:

```json
{"status": "OK"}
```

## Testing with chit-tui

:::note
chit-tui lives in this monorepo under `clients/chit-tui` (a nested Go
module). Build it with `make -C clients/chit-tui build` before following
the steps below.
:::

Point chit-tui at the Oathkeeper proxy (port 4455) and log in interactively:

```bash
export CHIT_SERVER_URL=http://localhost:4455
./clients/chit-tui/bin/chit-tui
```

The login screen will appear. Enter any user's email and password from the
table above. After successful login, the session token is stored at
`~/.config/chit/session.json` and reused on subsequent launches.

To force a fresh login, clear the stored session:

```bash
rm ~/.config/chit/session.json
```

Or use the `/logout` slash command in chit-tui.

## Running several clients at once

Anything involving two people — a mention arriving, a membership change
broadcasting, a reply appearing in someone else's thread — needs more than one
client. You can run as many as you like on a single machine.

:::caution[This is why a second client appears impossible]
Every client writes its session to the same file, `~/.config/chit/session.json`,
unless told otherwise. Start a second client without changing that and it
overwrites the first one's token: both windows end up logged in as whoever
authenticated last. Give each client its own `CHIT_SESSION_FILE` and they stay
independent.
:::

Give each client its own session file, and its own config file if you want to
tell them apart at a glance:

```bash
mkdir -p /tmp/uat

# Terminal 1 — alice
CHIT_SERVER_URL=http://localhost:4455 \
CHIT_SESSION_FILE=/tmp/uat/alice-session.json \
CHIT_CONFIG_FILE=/tmp/uat/alice-config.toml \
./clients/chit-tui/bin/chit-tui --theme tokyo-night

# Terminal 2 — bob
CHIT_SERVER_URL=http://localhost:4455 \
CHIT_SESSION_FILE=/tmp/uat/bob-session.json \
CHIT_CONFIG_FILE=/tmp/uat/bob-config.toml \
./clients/chit-tui/bin/chit-tui --theme catppuccin-latte

# Terminal 3 — chad
CHIT_SERVER_URL=http://localhost:4455 \
CHIT_SESSION_FILE=/tmp/uat/chad-session.json \
CHIT_CONFIG_FILE=/tmp/uat/chad-config.toml \
./clients/chit-tui/bin/chit-tui --theme kanagawa
```

Distinct themes are worth the trouble: with three identical windows it is easy
to type into the wrong one and misread the result.

### Skipping the login screen

Logging in three times is tedious. Point the client at chitd directly (port
8065, bypassing Oathkeeper) and present the user's Kratos ID as a header —
`CHIT_SESSION_TOKEN` is sent as whatever `CHIT_AUTH_HEADER` names:

```bash
CHIT_SERVER_URL=http://localhost:8065 \
CHIT_AUTH_HEADER=X-User-Id \
CHIT_SESSION_TOKEN=<kratos-id-from-seed-output> \
CHIT_SESSION_FILE=/tmp/uat/bob-session.json \
./clients/chit-tui/bin/chit-tui
```

Get the IDs from the database:

```bash
podman exec chit-uat-db-postgres psql -U chit -d chit \
  -tAc "select username || ' ' || kratos_id from users order by username;"
```

This trusts the header outright, so it is a UAT-only shortcut — it works
because chitd is reachable directly. Never expose port 8065 beyond the host.

### Driving clients without separate terminals

`tmux` runs each client in its own detached session, which is also how you
script a scenario:

```bash
tmux new-session -d -s uat-alice -x 120 -y 30 \
  "CHIT_SERVER_URL=http://localhost:8065 CHIT_AUTH_HEADER=X-User-Id \
   CHIT_SESSION_TOKEN=<alice-kratos-id> \
   CHIT_SESSION_FILE=/tmp/uat/alice-session.json \
   ./clients/chit-tui/bin/chit-tui --theme tokyo-night"

tmux send-keys -t uat-alice "/invite bob" Enter   # type into it
tmux capture-pane -t uat-alice -p                 # read the screen
tmux attach -t uat-alice                          # watch interactively
tmux kill-session -t uat-alice                    # done
```

`capture-pane -p -e` keeps the ANSI escapes, which is how you verify a theme
actually applied rather than just that the client started.

## Enabling slash commands

Slash commands are authorized through Keto, and a freshly seeded environment
grants nobody anything — `/invite`, `/kick` and even `/help` are all denied
until two things happen. Both are needed; the symptom of missing either is a
silent refusal with `"authorized":false` in the chitd log.

### 1. Push the command grants

`make uat-up` does not run the reconciler, so the role→command tuples do not
exist yet:

```bash
CHIT_DATABASE_URL="postgres://chit:chit@localhost:5432/chit?sslmode=disable" \
CHIT_KETO_WRITE_URL=http://localhost:4467 \
make reconcile
```

### 2. Bind the seeded users to roles

The reconciler reads actor→role bindings from `auth/actors/`, which ships with
its example commented out because user IDs are generated per environment. Bind
the seeded users directly:

```bash
bind() {  # $1=role  $2=user-id
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X PUT http://localhost:4467/admin/relation-tuples \
    -H 'Content-Type: application/json' \
    -d "{\"namespace\":\"chit/command\",\"object\":\"Role:$1\",
         \"relation\":\"member\",\"subject_id\":\"Actor:$2\"}"
}

while IFS='|' read -r name id; do
  case "$name" in
    alice)      role=admin ;;
    chit-agent) role=agent ;;
    *)          role=user  ;;
  esac
  printf '%-12s -> %-6s ' "$name" "$role"
  bind "$role" "$id"
done < <(podman exec chit-uat-db-postgres psql -U chit -d chit \
           -tAc "select username||'|'||id from users order by username;" | tr -d ' ')
```

Note the namespace is `chit/command`, not `command`; the wrong one returns
`404 Unknown namespace`.

Confirm a user can execute a command before testing through the UI:

```bash
curl -s -X POST http://localhost:4466/relation-tuples/check \
  -H 'Content-Type: application/json' \
  -d '{"namespace":"chit/command","object":"Command:invite",
       "relation":"execute","subject_id":"Actor:<alice-user-id>"}'
# {"allowed":true}
```

Use the chit **user** ID here (the `users.id` column), not the Kratos ID.

### Worked example: `/invite`

With two clients running and the steps above done:

1. As alice, create a channel bob is not in. An open channel automatically
   includes the whole team, so remove him first:
   ```bash
   curl -X DELETE -H "X-User-Id: <alice-kratos-id>" \
     "http://localhost:8065/api/v1/channels/<channel-id>/members/<bob-user-id>"
   ```
2. In alice's client, jump to that channel (`Ctrl+K`) and send `/invite bob`.
3. Alice sees an ephemeral reply attributed to `/invite`:
   `Added `bob` to the channel.` It is visible only to her and is not
   persisted.
4. In bob's client, press `Ctrl+K` — the channel now appears in his list.

Confirm server-side:

```bash
podman exec chit-uat-db-postgres psql -U chit -d chit -tAc \
  "select string_agg(u.username, ',' order by u.username)
     from channels c
     join channel_members cm on cm.channel_id = c.id
     join users u on u.id = cm.user_id
    where c.name = '<channel-name>';"
```

`/kick` follows the same flow. Removing yourself is leaving and any member may
do it; removing somebody else requires the `system_admin` role, so it succeeds
as alice and returns 403 as anyone else.

## Testing with curl

For direct API testing, you can still bypass auth by hitting the chitd server
directly (port 8065) with the `X-User-Id` header:

```bash
ALICE="X-User-Id: a11ce000-0000-4000-a000-000000000001"
BOB="X-User-Id: b0b00000-0000-4000-a000-000000000002"
```

:::caution[These IDs change once you seed Kratos]
The values above are the placeholders `scripts/seed-uat` assigns. Running
`make uat-seed-kratos` creates real Kratos identities and rebinds each user to
a new random ID, after which these headers resolve to nobody. Read the current
values instead:

```bash
podman exec chit-uat-db-postgres psql -U chit -d chit \
  -tAc "select username || ' ' || kratos_id from users order by username;"
```
:::

### Who am I

```bash
curl -H "$ALICE" http://localhost:8065/api/v1/users/me
```

### Post a message

Replace `CHANNEL_ID` with the Town Square channel ID from the seed output.

```bash
curl -X POST -H "$ALICE" -H 'Content-Type: application/json' \
  -d '{"channel_id":"CHANNEL_ID","content":"Hello from UAT!"}' \
  http://localhost:8065/api/v1/posts
```

### Read channel posts

```bash
curl -H "$ALICE" http://localhost:8065/api/v1/channels/CHANNEL_ID/posts
```

### Reply to a thread

Use the `root_id` field with the ID of the post you're replying to:

```bash
curl -X POST -H "$BOB" -H 'Content-Type: application/json' \
  -d '{"channel_id":"CHANNEL_ID","root_id":"POST_ID","content":"Threaded reply!"}' \
  http://localhost:8065/api/v1/posts
```

### The thread inbox

Replying to a thread starts following it. The author of the root post is
**not** followed automatically, so use the replier's header here — Bob's, if
he sent the reply above:

```bash
curl -H "$BOB" "http://localhost:8065/api/v1/users/me/teams/TEAM_ID/threads"
```

Each entry carries the root post, `last_viewed_at`, and `unread_mentions`. A
thread is unread when `thread.last_reply_at` is greater than `last_viewed_at`;
a never-read thread has `last_viewed_at` of `0`.

In chit-tui the same list is `/threads`: `enter` opens a thread (switching
channels if it lives elsewhere, and marking it read), `u` unfollows it, `esc`
closes the overlay.

### Search users

```bash
curl -H "$ALICE" 'http://localhost:8065/api/v1/users?term=bob'
```

### Create a DM channel

Pass an array of exactly two user IDs:

```bash
curl -X POST -H "$ALICE" -H 'Content-Type: application/json' \
  -d '["ALICE_USER_ID","BOB_USER_ID"]' \
  http://localhost:8065/api/v1/channels/direct
```

### List teams

```bash
curl -H "$ALICE" http://localhost:8065/api/v1/teams
```

### List channels in a team

```bash
curl -H "$ALICE" http://localhost:8065/api/v1/teams/TEAM_ID/channels
```

### Authenticated curl via Oathkeeper

To test the full auth flow with curl, first obtain a session token from Kratos:

```bash
# 1. Init a login flow
FLOW=$(curl -s http://localhost:4455/kratos/self-service/login/api | jq -r .id)

# 2. Submit credentials
TOKEN=$(curl -s -X POST \
  -H 'Content-Type: application/json' \
  -d '{"method":"password","identifier":"alice@example.com","password":"Password1!"}' \
  "http://localhost:4455/kratos/self-service/login?flow=$FLOW" \
  | jq -r .session_token)

# 3. Make authenticated requests through Oathkeeper
curl -H "X-Session-Token: $TOKEN" http://localhost:4455/api/v1/users/me
```

## How auth works

In the UAT environment, the full Ory stack is running:

1. **Oathkeeper** (port 4455) — auth proxy for all requests
2. **Kratos** (ports 4433/4434) — manages user identities and sessions
3. **Keto** (ports 4466/4467) — relationship-based authorization

The request flow is:
1. Client sends `X-Session-Token` header to Oathkeeper
2. Oathkeeper validates the session with Kratos (`/sessions/whoami`)
3. On success, Oathkeeper extracts `identity.id` and sets `X-User-Id` header
4. Oathkeeper forwards the request to chitd
5. chitd's `AuthExtract` middleware reads `X-User-Id` and calls `ProvisionUser`

Direct access to chitd on port 8065 bypasses Oathkeeper entirely. Since the
seed program pre-creates users with known Kratos IDs, `ProvisionUser` finds
them without calling Kratos.
