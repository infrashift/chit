description: Spin up a self-contained UAT environment with pre-seeded users for manual testing.

The UAT environment runs the full Ory stack (Kratos, Oathkeeper, Keto) with
chitd and PostgreSQL in a Podman pod. Five test users are pre-seeded with
Kratos identities so you can test both API access and chit-tui login.

## Prerequisites

| Dependency | Version | Purpose |
|---|---|---|
| Podman | 4.0+ | Run the UAT pod |
| Go | 1.24+ | Run the Kratos seed script |

## Start the environment

```bash
make uat-up
```

This builds the container images, creates a Podman pod, starts PostgreSQL,
runs migrations, seeds chit test data, and starts all services (Kratos,
Oathkeeper, Keto, chitd, Zincsearch, Vault).

Watch the server logs to confirm all services are ready:

```bash
podman logs -f chit-uat-app-chitd
```

### Seed Kratos identities

After the pod is fully running, create Kratos identities so users can log in:

```bash
make uat-seed-kratos
```

This creates password-based identities in Kratos for all 5 test users.
The script waits for Kratos to be ready before proceeding. It is idempotent
and safe to run multiple times.

## Verify

```bash
# Direct server access
curl http://localhost:8065/api/v1/system/ping

# Through Oathkeeper proxy
curl http://localhost:4455/api/v1/system/ping
```

Expected response:

```json
{"status": "OK"}
```

## Testing with chit-tui

Point chit-tui at the Oathkeeper proxy (port 4455) and log in interactively:

```bash
export CHIT_SERVER_URL=http://localhost:4455
./bin/chit-tui
```

The login screen will appear. Enter any user's email and password from the
table above. After successful login, the session token is stored at
`~/.config/chit-tui/session.json` and reused on subsequent launches.

To force a fresh login, clear the stored session:

```bash
rm ~/.config/chit-tui/session.json
```

Or use the `/logout` slash command in chit-tui.

## Testing with curl

For direct API testing, you can still bypass auth by hitting the chitd server
directly (port 8065) with the `X-User-Id` header:

```bash
ALICE="X-User-Id: a11ce000-0000-4000-a000-000000000001"
BOB="X-User-Id: b0b00000-0000-4000-a000-000000000002"
```

### Who am I

```bash
curl -H "$ALICE" http://localhost:8065/api/v1/users/me
```

### Post a message

Replace `CHANNEL_ID` with the Town Square channel ID from the seed output.

```bash
curl -X POST -H "$ALICE" -H 'Content-Type: application/json' \
  -d '{"channel_id":"CHANNEL_ID","message":"Hello from UAT!"}' \
  http://localhost:8065/api/v1/posts
```

### Read channel posts

```bash
curl -H "$ALICE" http://localhost:8065/api/v1/channels/CHANNEL_ID/posts
```

### Reply to a thread

Use the `root_id` field with the ID of the post you're replying to:

```bash
curl -X POST -H "$BOB" -H 'Content-Type: application/json' \
  -d '{"channel_id":"CHANNEL_ID","root_id":"POST_ID","message":"Threaded reply!"}' \
  http://localhost:8065/api/v1/posts
```

### Search users

```bash
curl -H "$ALICE" 'http://localhost:8065/api/v1/users?term=bob'
```

### Create a DM channel

Pass an array of exactly two user IDs:

```bash
curl -X POST -H "$ALICE" -H 'Content-Type: application/json' \
  -d '["ALICE_USER_ID","BOB_USER_ID"]' \
  http://localhost:8065/api/v1/channels/direct
```

### List teams

```bash
curl -H "$ALICE" http://localhost:8065/api/v1/teams
```

### List channels in a team

```bash
curl -H "$ALICE" http://localhost:8065/api/v1/teams/TEAM_ID/channels
```

### Authenticated curl via Oathkeeper

To test the full auth flow with curl, first obtain a session token from Kratos:

```bash
# 1. Init a login flow
FLOW=$(curl -s http://localhost:4455/kratos/self-service/login/api | jq -r .id)

# 2. Submit credentials
TOKEN=$(curl -s -X POST \
  -H 'Content-Type: application/json' \
  -d '{"method":"password","identifier":"alice@example.com","password":"Password1!"}' \
  "http://localhost:4455/kratos/self-service/login?flow=$FLOW" \
  | jq -r .session_token)

# 3. Make authenticated requests through Oathkeeper
curl -H "X-Session-Token: $TOKEN" http://localhost:4455/api/v1/users/me
```

## How auth works

In the UAT environment, the full Ory stack is running:

1. **Oathkeeper** (port 4455) — auth proxy for all requests
2. **Kratos** (ports 4433/4434) — manages user identities and sessions
3. **Keto** (ports 4466/4467) — relationship-based authorization

The request flow is:
1. Client sends `X-Session-Token` header to Oathkeeper
2. Oathkeeper validates the session with Kratos (`/sessions/whoami`)
3. On success, Oathkeeper extracts `identity.id` and sets `X-User-Id` header
4. Oathkeeper forwards the request to chitd
5. chitd's `AuthExtract` middleware reads `X-User-Id` and calls `ProvisionUser`

Direct access to chitd on port 8065 bypasses Oathkeeper entirely. Since the
seed program pre-creates users with known Kratos IDs, `ProvisionUser` finds
them without calling Kratos.

## Tear down

```bash
make uat-down
```

This removes the Podman pod and all its containers.

To also remove persistent volumes (database data):

```bash
make uat-clean
```
